# Frontend <-> API integration

## Objective
Replace the mocks of `apps/frontend/sumiclas-web` with the real backend API, in vertical slices, using the generated NSwag client (`src/modules/Shared/Infrastructure/GeneratedApiClient.ts`).

## Decisions (user)
- Follow the order below, point by point.
- Identity stays PROVISIONAL: on register the client generates the user id (`crypto.randomUUID()`), stores it in localStorage and sends it as `X-User-Id`. The Login page is not functional until real authentication exists (it says so). The password is never sent anywhere.
- CORS and JWT are explicitly postponed ("more ahead"): tracked in `apps/backend/AGENTS.md` ("Pendiente de decidir" and "REVISIÓN COMPLETA PENDIENTE"). Until then the browser reaches the API only through the Vite dev proxy (same origin).

## Constraints
- Frontend rules in `apps/frontend/AGENTS.md`: repository pattern in `modules/<module>/{domain,infrastructure}` injected through React Context, no TanStack Query, code in English, UI text in Spanish, typecheck + lint must pass.
- Privacy of minors: name + surname initial only, birthdays month/day only, photo opt-in.
- The backend is not changed in this feature unless a task says so.

## Known gaps (not solved by this feature)
- No endpoint to list class members (blocks expense participants and the class role page).
- No photo upload for lost items (the UI uses device-local `blob:` URLs).
- No dashboard summary, no school city, no teacher/AMPA roles.
- Creates return no body and ids are client-generated; the client must keep the ids it needs later (the wizard keeps them in `useWizardIds`). `enrollmentCreate` already creates a Confirmed enrollment, so there is no confirm step.
- The backend allows two schools with the same official code and two schools with the same name (no uniqueness rule yet); the wizard lets the user continue with either, so duplicates are possible.

## Acceptance
- A new user can register, create or join a class, and use each migrated screen against the real API in the browser.
- `pnpm typecheck` and `pnpm lint` pass after every task.

## Route declaration
- Exploration: delegated (one read-only mapper, 4+ files).
- Each task: one delegated writer (2+ non-trivial files).

## Review follow-ups (non-blocking findings from the native reviews, NOT done yet)
Source: the advisory findings of the approved reviews of commits 3f6c3ff, 17b62a4, 17b38cd, 02e5e80, f2d166c and 5ede840. None blocked a commit; fix them in a dedicated pass (or when the code is touched again). Do not re-review old commits for them.

Identity and registration
- Register is not idempotent: a retry after a lost response sends a new id with the same email and gets a conflict; `setSubmitting(true)` runs before `crypto.randomUUID()`, which only exists in secure contexts (HTTPS or localhost), so on plain HTTP the button can stay on "enviando".
- The user id lives in localStorage and defines the session (provisional identity; replaced by JWT, see backend AGENTS.md "CORS" and "JWT").

Client plumbing
- `getApiErrorMessage` treats every `TypeError` as a network failure, hiding programming errors.
- Date revival only covers a fixed list of keys (`createdAt`, `dueDate`, `date`, `startDate`, `endDate`) and date-times must carry an offset; a new `Date` field in a DTO stays a string at runtime. `toApiDateOnly` returns a `Date` with an overridden `toJSON`, which is easy to lose by cloning or spreading.
- `NSwagUserRepository.toClassRole` maps any unknown role to `participant` silently; priority/role mapping in the announcement repository does the same (`normal` / `participant`). Prefer an explicit unknown fallback or a dev warning.
- `formatStudentName` breaks on an empty or missing `surnameInitial`.

Contexts and pages
- `ChildProvider`: the representative actions are silent no-ops and `otherGuardians` is empty without any comment in the code (documented only here); `errorStatus` is exposed but unused; the `ChildView` doc says labels are never empty while `schoolName` can be `''`; the `participant` default when the profile has no role for the class is implicit.
- Onboarding: `handleCreateClass` and `handleConfirmStudent` return silently when their guard fails, leaving the submit button disabled; the school search can keep "Buscando..." if the query is cleared while a request is in flight.
- Announcements: (1) "Cargar más" failing for the previous class after switching child shows its error on the new class, and `loadingMore` is not reset; (2) the create form shows even when the child has no class and then does nothing silently; (3) the id policy treats every status below 500 as definitive: 408 and 429 should keep the id, and a 409 after a lost response should reload the list and warn (as the class creation in onboarding does); (4) the unread/urgent filters only apply to the pages already loaded, so "No hay avisos por ahora" can show while more pages exist (say so when `nextCursor` is present).

Backend gaps seen from the frontend
- Repeating the id of an already saved lost item (lost response and retry) answers 500 instead of 409 (verified in T4.2); other client-generated-id creates probably do the same.
- Two schools with the same official code or name are accepted and the wizard does not warn.
- It is not known which backend rule returns the 409 for a repeated class id (no duplicate check found in the `Classes` module); class names are not validated for duplicates within a school year.
- No endpoint lists the members of a class (blocks T4.5 expenses and T4.6 class-role page) or the students of a class (blocks "join as second guardian").
