# Integración del frontend con la API

Aplica a `apps/frontend/sumiclas-web/**`. Las reglas obligatorias, la tabla de skills y lo pendiente de decidir están en `apps/frontend/AGENTS.md`; las convenciones comunes de idioma, commits y ramas, en el `AGENTS.md` de la raíz.

## Cliente generado y plumbing

- **Cliente HTTP**: generado por **NSwag** a partir del OpenAPI del backend (`/openapi/v1.json`, **protegido con Bearer incluso en Development**). Vive en `src/modules/Shared/Infrastructure` (`GeneratedApiClient.ts` + `GeneratedApiClient.nswag` + `ClientBase.ts`) y es compartido por todos los módulos. No escribas `fetch`/`axios` a mano contra los endpoints — usa el cliente NSwag. **Única excepción**: `isPasswordPwned` (`lib/validation.ts`, usada en `pages/Register.tsx`) llama con `fetch` a `https://api.pwnedpasswords.com/range/` (Pwned Passwords), que no es la API de SumiClas; usa k-anonimato (solo envía los 5 primeros caracteres del hash SHA-1 de la contraseña, nunca ella ni el hash completo) y falla en abierto (si la consulta falla, devuelve `false` y el registro no se bloquea). Hoy el cliente generado **se comitea** y se regenera con `pnpm generate:client` (levanta una API temporal con el código actual, necesita PostgreSQL arriba porque la API aplica las migraciones pendientes al arrancar; ver `Readme.md`). Como el documento exige Bearer, el script arranca esa API con una clave de firma propia y desechable (`Jwt__SigningKey`, aleatoria en cada ejecución, que tiene prioridad sobre los User Secrets: no lee los secretos del usuario), fabrica un JWT HS256 de 5 minutos con los `iss`/`aud` de `appsettings.json` y lo envía como `Authorization: Bearer` al descargar el documento. Con `--url` (una API ya en marcha) se pasa un token propio con `--token <jwt>` o la variable `SUMICLAS_OPENAPI_TOKEN`. No se edita `GeneratedApiClient.ts` a mano.
- **Plumbing del cliente (`ApiClient.ts`, `apiDate.ts`)**: `createApiClient()` construye el cliente con `authHttp` (ver la skill `frontend-auth-session`) y `baseUrl` **`/api`** (`API_BASE_URL`, en `authHttp.ts`) (sin barra final: el cliente concatena `baseUrl + "/ruta"`). En desarrollo, Vite reenvía `/api` a la API **quitando el prefijo** (`vite.config.ts`: destino `API_PROXY_TARGET`, por defecto `https://localhost:7064`, `secure: false` por el certificado de desarrollo). El navegador solo habla con el origen de Vite, así que hoy no hace falta CORS. El cliente se obtiene con `useApiClient()` (`ApiClientProvider` en `main.tsx`); no instancies `GeneratedApiClient` a mano.
- **Fechas**: los DTO generados tipan las fechas como `Date` pero `JSON.parse` deja texto. `ApiClient` sobrescribe `jsonParseReviver` y convierte solo las claves conocidas (`createdAt` como fecha-hora; `dueDate`, `date`, `startDate`, `endDate` como fecha sin hora, a medianoche **local** para que no cambie de día con la zona horaria); un texto libre con forma de fecha no se toca. Al **enviar** un campo de solo fecha, envuélvelo con `toApiDateOnly(date)`: la API espera `yyyy-MM-dd` y un `Date` normal se serializa como fecha-hora UTC. Si el DTO generado añade otra clave de fecha, añádela a las listas de `ApiClient.ts`.
- **Errores del cliente generado**: cuando la respuesta de error trae cuerpo (los 400, 401, 403, 404 y 409 de la API lo traen), el cliente **lanza el propio objeto `ProblemDetails`** (con `status`, `title` y el `code` del error de dominio), **no** una `ApiException`. `ApiException` solo se lanza para respuestas sin cuerpo o con un estado no declarado. Quien capture errores debe tratar ambos casos.
- **Mensajes de error en la UI**: `getApiErrorMessage(error)` (`src/lib/apiError.ts`) convierte lo que lanza el cliente (`ProblemDetails` con `code`, `ApiException` o el `TypeError` de un fallo de red) en un mensaje en español: usa el texto propio de los códigos conocidos (`User.EmailAlreadyRegistered`...), el `detail` en español de los demás errores de dominio y, si no hay, uno genérico por estado. `getApiErrorStatus(error)` devuelve el estado HTTP. El backend documenta en OpenAPI los errores 400, 401, 403, 404 y 409 de cada operación como un único `ProblemDetails` (`ProblemResponsesTransformer`), así que el cliente generado lanza `ProblemDetails` con su `code` en todos ellos; una `ApiException` solo llega para los estados no documentados, como el 500.

## Repositorios ya creados

- **Repositorios ya creados**: `modules/sessions` (`ISessionRepository`: `login(newSession): Session`, `refresh(): Session`, `logout()`; tipos `NewSession` y `Session` (`{ accessToken, expiresAt, userId, fullName }`); `NSwagSessionRepository`, inyectado con `SessionRepositoryProvider` y `useSessionRepository()` en `main.tsx`), `modules/users` (`IUserRepository`: `getCurrent`, `listClassMembers`, `register(newUser)`, `changeName(fullName)`, `changePassword(current, new)` (el servidor revoca todas las sesiones: quien llama debe cerrar la local con `useAuth().signOutLocally()`); tipo `NewUser`), `modules/students` (`IStudentRepository`: `listMine`, `register`, `changeName(studentId, StudentName)`; `Child` lleva ahora `firstName`) y, para el onboarding, `modules/provinces` (`IProvinceRepository`: `listAll`), `modules/localities` (`ILocalityRepository`: `listByProvince(provinceId, name?)`), `modules/schools` (`ISchoolRepository`: `findByLocality(localityId, name?)`, `findById`; ya no existe el alta libre de colegios), `modules/schoolYears` (`ISchoolYearRepository`: `listActive`, `create`), `modules/classes` (`IClassRepository`: `listBySchoolYear`, `create`) y `modules/enrollments` (`IEnrollmentRepository`: `create`), cada uno con su implementación `*Http`. Los cuatro de colegios, cursos, clases y matrículas se inyectan juntos con `OnboardingRepositoriesProvider` y `useOnboardingRepositories()`; provincias y poblaciones tienen cada una su contexto (`ProvinceRepositoryProvider`/`useProvinceRepository()`, `LocalityRepositoryProvider`/`useLocalityRepository()`, montados en `main.tsx`). Se inyectan con `UserRepositoryProvider` y `StudentRepositoryProvider` (montados en `main.tsx`, dentro de `ApiClientProvider`) y se usan con `useUserRepository()` y `useStudentRepository()`. La capa `infrastructure` traduce los enums de la API (PascalCase) a los de la UI (`ClassRepresentative` → `classRepresentative`) y los `null` de la API a `undefined`.

## Patrón repositorio e inyección

- **Patrón repositorio**, en `src/modules/<module>/`:
  - `domain/` — un fichero por tipo (nombre del fichero = nombre del tipo): el contrato del repositorio (ej. `IAnnouncementRepository`, en `domain/IAnnouncementRepository.ts`) contiene **solo la interfaz**, y cada tipo de dominio del módulo va en su propio fichero (`Announcement.ts`, `AnnouncementPage.ts`, `NewAnnouncement.ts`...). Los tipos compartidos entre módulos (p. ej. `PageRequest`) viven en `modules/Shared/domain/`. Sin ficheros índice ni reexportaciones: cada uno se importa desde su fichero. No depende de `infrastructure` ni del cliente NSwag.
  - `infrastructure/` — implementación concreta del repositorio (ej. `NSwagAnnouncementRepository`) que usa el cliente compartido de `modules/Shared/Infrastructure` para hacer las llamadas reales.
  - No se usa TanStack Query ni ninguna librería de caché de peticiones para esto.
- **Inyección de la implementación**: mediante un Contexto de React (mismo patrón que `ChildContext`/`ChildProvider`), no como singleton importado directamente ni instanciado a mano en el componente. Esto permite sustituir la implementación por un mock en los tests de `apps/test/frontend`. Componentes y hooks (en `components/app/`) consumen el repositorio a través de un hook propio (p. ej. `useAnnouncementRepository()`), nunca instanciando `NSwagAnnouncementRepository` directamente.
- Los mocks de `src/data/*.ts` se sustituyeron por `modules/<module>/` **módulo a módulo**, no todos a la vez; hoy en `src/data` solo queda `featureMeta.ts`, que es de la landing y no habla con la API.
