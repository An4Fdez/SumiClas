# Notas por pantalla del frontend

Aplica a `apps/frontend/sumiclas-web/**`. Las reglas obligatorias, la tabla de skills y lo pendiente de decidir están en `apps/frontend/AGENTS.md`; las convenciones comunes de idioma, commits y ramas, en el `AGENTS.md` de la raíz.

## Estado de la conexión con la API

- **Hoy**: ya usan la API real el registro, el perfil del usuario y sus alumnos (`ChildProvider`). El onboarding (colegio, curso escolar, clase, alumno y matrícula), los avisos, los objetos perdidos y el calendario también usan la API real. Los deberes (con sus asignaturas) también usan la API real. Los gastos también usan la API real, con la lista de miembros de la clase para elegir participantes (**verificado en un Chrome real contra la API real y PostgreSQL, 72 comprobaciones**). El dashboard también usa la API real para sus contadores (**verificado en un Chrome real contra la API real y PostgreSQL**). El resumen semanal con IA también usa la API real (ver «Resumen semanal con IA» más abajo) y `src/data/appMock.ts` ya no existe.

## ChildProvider (alumnos, perfil y rol)

- **`ChildProvider`**: al montarse carga `studentRepository.listMine()` y `userRepository.getCurrent()`, y expone `loading`, `error`, `errorStatus` y `reload`; `AppLayout` muestra "Cargando tu información…" o el error con "Reintentar" y "Cerrar sesión" (necesario si el usuario de la sesión ya no existe en la API: responde 404). `currentRole` sale de `classRoles` buscando el `classId` del hijo (sin clase, `null`). Un hijo sin matrícula confirmada en un curso activo se muestra como "Sin clase". El nombre del alumno es `firstName + surnameInitial`: la API ya manda la inicial con su punto ("P."), no se añade otro. El resumen del dashboard ya no pasa por este contexto: lo carga la propia página (ver "Resumen del dashboard"). El contexto expone `refresh()`, que recarga alumnos y perfil **sin** mostrar la pantalla de carga y, si falla, deja en pantalla los datos que ya había (lo usa la gestión de delegados para actualizar el rol tras nombrar o renunciar). El contexto expone además `currentUserId` (el id del perfil que `ChildProvider` ya carga), que los gastos usan para saber qué participación es la tuya. **Limitación conocida**: `refresh()` no secuencia ni cancela peticiones, así que dos refrescos que se solapan, o uno junto a un `reload`, pueden terminar fuera de orden y devolver un `currentRole` antiguo; uno que llega mientras se está cargando se descarta.

## Notas por pantalla

- **Onboarding (`pages/Onboarding.tsx` + `components/onboarding/*`)**: (1) colegio: provincia -> población -> colegio. `useProvinces` carga las 52 provincias; `useProvinceLocalities(provinceId)` carga **todas** las poblaciones de la provincia (la API no pagina; la mayor tiene 299) y `useLocalitySchools(localityId, name)` pide `schoolFinderByLocality` con el nombre con debounce de 300 ms (la API devuelve como mucho 50 colegios y el filtro ignora tildes y mayúsculas); los tres usan una guarda de generación para descartar respuestas y errores tardíos. Cambiar de provincia reinicia población y búsqueda; cambiar de población reinicia solo la búsqueda. Provincia y población usan `components/app/SearchableSelect.tsx` (campo con filtro en el cliente sin tildes, máximo 100 opciones visibles; se eligió en vez de `SelectDropdown`, que no tiene filtro, y de un `<select>` nativo, prohibido por el diseño) y los resultados muestran nombre, dirección, código postal y población y teléfono. **No existe alta de colegios**: solo se eligen los del catálogo oficial, y se quitaron el formulario, el caso de uso y el id `school` del asistente. (2) clase: `useSchoolClasses` busca el curso escolar **activo** del colegio y, si no hay, crea el actual (`lib/schoolYear.ts`: del 1 de septiembre al 30 de junio; si el mes es septiembre o posterior empieza este año natural, si no el anterior) y lista sus clases; crear una clase deja al creador como delegado (lo hace el servidor). (3) alumno: `studentRegister` (el primer tutor es el usuario actual) y `enrollmentCreate`, que ya crea la matrícula **confirmada** (no hace falta `enrollmentConfirm`; comprobado en PostgreSQL). **Ids**: los genera el cliente y un id repetido da error en el backend (comprobado con una clase cuya respuesta se perdió: 409 `conflicto`, sin duplicados; el backend responde 409 también en las demás entidades), por eso `useWizardIds` reutiliza el id de un intento fallido (`take`) y lo descarta al tener éxito (`consume`), y el asistente guarda el alumno ya registrado para que un reintento solo repita la matrícula. **Limitación conocida**: tras un 409, los pasos de colegio, alumno y matrícula conservan el mismo id del asistente, así que si la respuesta se perdió después de guardarse, cada reintento vuelve a dar 409 (el colegio ya no se crea, así que no cuenta); solo la creación de la clase descarta el id y recarga la lista. Habría que tratar ese 409 como «ya creado» y continuar con lo guardado. **Verificado** en un Chrome real contra la API real (alta de colegio, curso escolar automático sin duplicados, clase con delegado, unirse a una clase existente como participante, reintentos sin duplicados y privacidad de apellidos). **Hueco conocido**: ya no se ofrece "unirse como segundo tutor" ni se detectan alumnos duplicados, porque la API no tiene un endpoint para listar los alumnos de una clase y `studentGuardianAdd` exige ser ya tutor del alumno.
- **Avisos (`pages/Announcements.tsx`, `modules/announcements`)**: `IAnnouncementRepository` (`listByClass`, `create`, `update`, `remove`, `markAsRead`) se inyecta con `AnnouncementRepositoryProvider` y `useAnnouncementRepository()`; `useClassAnnouncements(classId)` carga la primera página de la clase del hijo seleccionado (la API devuelve juntos los avisos del colegio y los de la clase, del más reciente al más antiguo), pide más con el cursor (`Cargar más`, sin duplicados) y marca como leído de forma optimista (`PUT /read`, que revierte si falla y muestra el error con `readError`, como las demás marcas). **El orden es el de la API**: no se reordena por prioridad en el cliente (no es compatible con la paginación por cursor); los filtros (colegio/clase, urgentes, leídos/no leídos) actúan sobre lo ya cargado. **El autor del aviso (`isAuthor`) ve «Editar» y «Eliminar» en el detalle:** «Editar» abre `AnnouncementForm` en modo edición (título, mensaje, prioridad y evento relacionado; avisa de que al guardar el aviso vuelve a quedar como no leído para las familias) y «Eliminar» pide confirmación en línea (`RepresentativeConfirm`) y borra para todas las familias; ambos recargan la lista. Un aviso editado lleva la etiqueta «editado» (`updatedAt`) en la tarjeta y en el detalle. **«No leídos» viene activo por defecto** al abrir la pantalla: si no queda ninguno, el mensaje de lista vacía lo explica y, si hay más páginas, invita a «Cargar más». El estado de lectura es del servidor: ya no existe "marcar como no leído". Un hijo sin clase muestra un mensaje y **no hace ninguna petición**. Solo el delegado (`currentRole === 'classRepresentative'`) ve "Nuevo", y solo se ofrece ámbito de clase (los avisos oficiales de colegio son del rol de administrador del colegio, que no existe aún). El id del aviso lo genera el cliente con `useWizardIds`: se conserva tras un fallo de red o 5xx y se descarta tras el éxito o un 4xx definitivo. El selector de evento relacionado está oculto hasta migrar el calendario (T4.3), pero el aviso que ya traiga `relatedEvent` lo muestra. Verificado en un Chrome real contra la API real (27 comprobaciones: crear, leído, paginación con 25 avisos, otra clase sin fugas, hijo sin clase, reintento tras fallo de red y modo oscuro).
- **Ámbito colegio cerrado en esta versión** (decisión del usuario, 2026-10-23): el backend rechaza publicar avisos, eventos y objetos perdidos con ámbito colegio (403 `User.SchoolPublishForbidden`; ver "Ámbito colegio" en la skill `backend-authorization`) hasta que existan los roles de admin del colegio y de profesor. Los formularios no ofrecen ese ámbito (crean siempre con `scope: 'class'`) y las pantallas de avisos, calendario y objetos perdidos ya no muestran la pestaña de filtro "Colegio", que saldría siempre vacía. Se conservan los tipos `AnnouncementScope`, `EventScope` e `ItemScope` con `'school'`, las etiquetas "Colegio" de las tarjetas y el filtro por ámbito para cuando se abra. **Para abrirlo**: devolver los roles en el perfil del usuario, ofrecer el ámbito colegio en los formularios solo a quien puede publicarlo y volver a añadir `{ value: 'school', label: 'Colegio' }` a `scopeFilters` en las tres pantallas.
- **Objetos perdidos (`pages/LostAndFound.tsx`, `modules/lostItems`)**: `ILostItemRepository` (`listByClass`, `create`, `markAsRecovered`, `markAsNotRecovered`) con `NSwagLostItemRepository`, inyectado con `LostItemRepositoryProvider` y `useLostItemRepository()` (en `main.tsx`). `useClassLostItems(classId)` carga la primera página de la clase del hijo seleccionado y, con "Cargar más", las siguientes por cursor (sin duplicados); una **generación** (`generation`) se invalida al cambiar de clase o recargar, así que una respuesta o un error tardío de la clase anterior nunca llega a la nueva, y al cambiar de clase se reinician "cargando más" y su error. El estado **recuperado es del servidor y reversible**: `setRecovered(id, true|false)` llama a `markAsRecovered` o `markAsNotRecovered` con actualización optimista que se revierte (con mensaje en español) si falla. Los filtros de la página (alcance y estado) solo actúan sobre lo ya cargado, y si hay más páginas el mensaje de lista vacía lo dice. **Solo se crea con ámbito de clase** (el backend rechaza el ámbito colegio mientras no existan los roles de admin y de profesor, ver "Ámbito colegio cerrado en esta versión") y el botón "Nuevo" solo sale si el hijo tiene clase. **Quién marca como recuperado**: el backend lo permite solo al autor del objeto, así que `ItemCard` e `ItemDetailModal` reciben `canToggleRecovered` (`item.authorId === currentUserId`): el autor ve el botón y el resto solo ve una marca de «Recuperado» si ya lo está. **Ids**: el de un intento fallido se conserva ante un fallo de red, 5xx, 408 o 429 y se descarta tras éxito o un 4xx definitivo; un 409 recarga la lista y avisa con `UserFacingError` (ese aviso del 409 se comprobó a través de la API, aún no desde la interfaz). **Fotos (hueco conocido)**: la API solo guarda una URL (`photoUrl`, máx. 2048) y no hay endpoint para subir la imagen; la interfaz usaba URLs `blob:` locales que otros usuarios no pueden abrir, así que **se ocultó el campo de foto y nunca se envía `photoUrl`** (siempre `photoPrivacyConfirmed: false`); si la API devuelve un objeto con `photoUrl` se muestra. Habrá que decidir cómo subir imágenes antes de volver a ofrecerlo. Repetir el id de un objeto ya guardado (respuesta perdida y reintento) responde 409 en el backend, así que el aviso del 409 y la recarga de la lista se aplican. **Editar y eliminar:** el autor ve «Editar» y «Eliminar» en el detalle; «Editar» reutiliza `ItemForm` y **solo deja cambiar la descripción** (el tipo se muestra pero no cambia, y «recuperado» se conserva). Lo ve el delegado, pero no puede tocar lo de otra persona.
- **Calendario (`pages/Calendar.tsx`, `modules/calendarEvents`)**: `ICalendarEventRepository` (`listByClass`, `create`, `createBirthday`) con `NSwagCalendarEventRepository`, inyectado con `CalendarEventRepositoryProvider` y `useCalendarEventRepository()` (en `main.tsx`). `useClassCalendarEvents(classId)` carga **todos** los eventos de la clase del hijo seleccionado (los del colegio, los puntuales de la clase y los cumpleaños de sus alumnos; la API no pagina ni filtra por mes, así que mes/semana/lista y los filtros son del cliente) con la misma guarda de generación que los demás hooks. Un evento tiene `month`, `day` y `year?`: **un cumpleaños no tiene año** (se repite cada año y nunca se guarda el año de nacimiento), uno puntual sí. `lib/date.ts` ya no usa el año centinela de 1900: `occurrenceInYear`, `eventOccursOnDay`, `nextOccurrence` y `visibleYearForEvent` reciben `{ month, day, year? }`, y un 29 de febrero recurrente cae el **28 de febrero** en los años no bisiestos. `eventTypeMeta` vive en `lib/eventTypeMeta.ts`. Al crear: solo ámbito de clase (los eventos de todo el colegio son del administrador del colegio, que no existe como rol); el delegado ve el selector de tipo y cualquier tutor ve solo el formulario de cumpleaños de **su** hijo (el título se construye con `studentName`); la fecha se envía con `toApiDateOnly` y la hora como `HH:mm` (la API la devuelve como `HH:mm:ss` y el repositorio la recorta); el id se guarda por clase y contenido exacto (otro contenido recibe otro id), se conserva ante fallo de red, 5xx, 408 y 429 y se descarta tras éxito o un 4xx; un 409 recarga y avisa. El selector de **evento relacionado** de los avisos vuelve a estar activo con los próximos eventos puntuales de la clase (sin cumpleaños). **Verificado** en un Chrome real contra la API real, incluidas las zonas UTC+14 y UTC-8 sin desfase de día. **Editar y eliminar:** el autor de un evento ve «Editar» y «Eliminar» en el detalle (`?event=<id>` lo abre directamente); «Editar» reutiliza `EventForm` con el evento (sin la opción «Cumpleaños»). **Un cumpleaños solo se elimina** (su autor ve «Eliminar», nunca «Editar»). Un evento editado lleva «editado» en el detalle.
- **Deberes (`pages/Homework.tsx`, `modules/assignments`, `modules/subjects`)**: `IAssignmentRepository` (`listByClass`, `create`, `addComment`, `markAsDone`, `markAsNotDone`) con `NSwagAssignmentRepository` y `ISubjectRepository` (`listByClass`, `create`) con `NSwagSubjectRepository`, inyectados juntos con `HomeworkRepositoriesProvider` y `useHomeworkRepositories()` (en `main.tsx`). `useClassAssignments(classId)` carga la primera página (la API ordena por fecha de entrega ascendente y trae los comentarios dentro de cada tarea), pagina con «Cargar más» y descarta las respuestas y errores tardíos de otra clase (generación) también al cambiar de hijo; `useClassSubjects(classId)` carga las asignaturas. Un hijo sin clase muestra un mensaje y no hace peticiones. **Asignaturas**: la API solo tiene `{id, classId, label}` y **no hay catálogo por defecto**; solo el delegado de la clase las crea (en el formulario, «Añadir asignatura»), y un participante de una clase sin asignaturas ve que el delegado tiene que crearlas antes y no puede proponer. El color de una asignatura no existe en la API: sale de un hash estable de su id (`lib/subjectColor.ts`), no de su posición en la lista. **Oficial o propuesta**: lo decide el servidor (`isProposal`, `false` si quien crea es delegado de esa clase); la UI solo muestra la insignia «Propuesta». **No hay endpoint para aprobar** una propuesta, así que la UI no ofrece aprobarla. **Comentarios**: `addComment` crea el comentario con el usuario actual; se añade de forma optimista y se revierte con un mensaje en español si falla. **«Hecho»**: es una marca **personal y del servidor** (`PUT`/`DELETE /assignments/{id}/done`, idempotentes): cada usuario solo ve y cambia la suya, y se ve en cualquier dispositivo. La lista trae `done` en cada tarea (`Assignment.done`) y `useClassAssignments.setDone(id, done)` la cambia con actualización optimista que se revierte con un mensaje en español (`doneError`) si falla; mientras una petición del mismo deber sigue en curso, otro clic se ignora. Ya no existe `useDoneAssignments` ni el `localStorage`; las marcas que había guardadas en el navegador no se migraron. Se puede marcar un deber de un curso no activo. **Fechas**: la fecha de entrega es solo fecha (medianoche local) y se envía con `toApiDateOnly`; las etiquetas salen de `formatDueDate` y `formatDayHeading` (`lib/date.ts`). **Ids de creación**: ligados a la clase y al contenido exacto del formulario (`assignment:<classId>:<json>`), se conservan ante fallo de red, 5xx, 408 y 429 y se descartan tras éxito o un 4xx definitivo; un 409 recarga la lista y avisa con `UserFacingError`. Los filtros de asignatura y de pendientes/hechas solo actúan sobre lo ya cargado y el mensaje de lista vacía lo dice cuando hay más páginas. **Verificado** en un Chrome real contra la API real (asignaturas, tarea oficial y propuesta, fechas sin desfase en tres husos horarios, comentarios con reversión, paginación con 29 tareas, otra clase, hijo sin clase, fallo de red al crear, respuestas tardías al cambiar de hijo y modo oscuro). **Editar y eliminar:** el autor ve «Editar» y «Eliminar» en el detalle; «Editar» reutiliza `AssignmentForm` con el deber (asignatura, título, descripción y fecha) y avisa de que **al guardar la tarea vuelve a quedar pendiente para todas las familias** (los comentarios se conservan); eliminar borra también sus comentarios y marcas. Una propuesta de familia la edita y elimina su autor, no el delegado.
- **Gastos (`pages/Expenses.tsx`, `modules/classExpenses`)**: `IClassExpenseRepository` (`listByClass`, `create`, `markAsPaid`, `markAsUnpaid`) con `NSwagClassExpenseRepository`, inyectado con `ClassExpenseRepositoryProvider` y `useClassExpenseRepository()` (en `main.tsx`). `useClassExpenses(classId)` carga la primera página de la clase del hijo seleccionado (más recientes primero; cada gasto trae sus participantes con `hasPaid`), pagina con «Cargar más» y descarta las respuestas y errores tardíos de otra clase (generación). Un hijo sin clase muestra un mensaje y no hace peticiones. **Quién paga**: cada participante marca o desmarca **solo su propio** pago (`PUT`/`DELETE` de `paid`, idempotentes), con actualización optimista que se revierte con un mensaje en español si falla y un segundo clic ignorado mientras la petición sigue en curso; el backend deja que cada familia de la clase marque su propia parte y reserva marcar la de otra persona al delegado (la interfaz solo ofrece la propia). **Crear**: solo el delegado (`currentRole === 'classRepresentative'`). Los participantes se eligen de la lista de miembros de la clase (`useClassMembers`, que solo se pide mientras el formulario está abierto; un no miembro recibe un 403 que se muestra dentro del selector con «Reintentar»), por defecto todos. **Dinero**: el importe se escribe por familia y `lib/money.ts` lo convierte a **céntimos enteros** (`parseEuroAmount`), así que más de 2 decimales se rechaza en el formulario con un mensaje y el total nunca pasa por aritmética de coma flotante (`totalAmount = céntimos / 100`, máximo 99.999.999,99 €, la columna es `decimal(10,2)` y redondearía en silencio); se muestra con `Intl.NumberFormat('es-ES', EUR)` (`formatEuros`). El concepto admite 200 caracteres (límite del backend). **Evento relacionado**: `useUpcomingEventOptions(classId)` ofrece los próximos eventos puntuales de la clase (sin cumpleaños) y se envía `relatedEventId`. **Ids de creación**: ligados a la clase y al contenido exacto del formulario, se conservan ante fallo de red, 5xx, 408 y 429 y se descartan tras éxito o un 4xx definitivo; un 409 recarga y avisa con `UserFacingError`. Los filtros «Pendientes/Pagados» solo actúan sobre lo ya cargado y el mensaje de lista vacía lo dice cuando hay más páginas. Un rol de autor desconocido queda `undefined` (`parseClassRole` en `lib/roles.ts`) en vez de convertirse en participante. **Estado**: verificado contra la API real y PostgreSQL con un Chrome headless (72 comprobaciones: crear con participantes reales, céntimos, pagar/desmarcar con recarga y reversión sin red, paginación con 25 gastos, aislamiento entre clases, reintento tras fallo de red con un solo gasto, cambio de hijo con petición en vuelo, 403 en el selector, evento relacionado, modo oscuro). Si se pierde la respuesta de crear tras guardarse el gasto, el reintento con el mismo id devuelve 409 (no se duplica). **Editar y eliminar:** el autor (el delegado que lo creó) ve «Editar» y «Eliminar» en el detalle; «Editar» reutiliza `ExpenseForm` con el gasto: **no se cambian los participantes** (el formulario lo dice), el importe que se pide es el **total** y **los pagos ya marcados se mantienen**; **un gasto con algún pago ya hecho no se puede eliminar**: el detalle cambia «Eliminar» por un aviso («No se puede eliminar este gasto porque una familia ya ha pagado» o «… porque N familias ya han pagado») y el servidor lo rechaza igualmente con `ClassExpense.HasPayments` (400, el mensaje en español llega tal cual); «Editar» sigue disponible. Si nadie ha pagado, eliminar pide confirmación («Se borrará para todas las familias. No se puede deshacer.»).
- **Resumen del dashboard (`pages/Dashboard.tsx`, `modules/dashboard`)**: `IDashboardRepository.getSummary(classId, days)` con `NSwagDashboardRepository` (llama a `GET /dashboard/summary`), inyectado con `DashboardRepositoryProvider` y `useDashboardRepository()`; `useClassDashboardSummary(classId, days)` carga con el mismo patrón de `generation` que el resto de hooks y devuelve `state` (`idle` sin clase, `loading`, `ready`, `error`) y `reload`. `DashboardSummary` es el tipo de dominio (`announcements.unread/urgent`, `homework.pending/nextDueDate`, `expenses.pending/item`, `lostAndFound.count`, `upcomingEvents[]` con título, tipo, fecha y días que faltan); `nextDueDate` se revive como fecha local en `apiDate.ts`. La página tiene un selector de periodo (`SUMMARY_PERIODS` = 7, 14 o 30 días, 7 por defecto, en `modules/dashboard/domain/SummaryPeriod.ts`) que cambia la petición: afecta a avisos sin leer, objetos perdidos y a cuántos días hacia delante se listan los eventos; deberes y gasto no dependen de él. El calendario enseña el primer evento de la lista («y N más» si hay más); un alumno sin clase muestra un aviso en vez de tarjetas; un fallo muestra el mensaje con «Reintentar». **Verificado en un Chrome real contra la API real y PostgreSQL** (periodos 7/14/30, el que publica no ve sus avisos como sin leer, API caída → error con «Reintentar»).
- **Resumen semanal con IA (`components/app/WeeklySummaryCard.tsx`, `modules/weeklySummary`)**: `IWeeklySummaryRepository.generate(classId)` con `NSwagWeeklySummaryRepository` (llama a `POST /weekly-summaries?classId=`), inyectado con `WeeklySummaryRepositoryProvider` y `useWeeklySummaryRepository()`. `useClassWeeklySummary(classId)` lo pide al abrir el dashboard (y cada vez que cambia la clase) y devuelve `state` (`idle` sin clase, `loading`, `ready`, `error`) y `generate` (vuelve a pedirlo); ante un 409 (dos familias abriendo a la vez, la que pierde la carrera de guardar) pide una vez más y encuentra el resumen guardado, y si vuelve a fallar muestra el error. El servidor solo llama a la IA cuando la semana ha cambiado desde el último texto, así que abrir el dashboard es barato. `WeeklySummary` es el tipo de dominio (`weekStart`, `weekEnd`, `lines[]` con una frase por línea, vacío si la semana no tiene novedades, y `generatedAt`); `weekStart`/`weekEnd` se revén como fechas locales y `generatedAt` como fecha-hora en `apiDate.ts`. La tarjeta muestra «Preparando el resumen de la semana…» mientras carga, las frases con «Generado con IA · hace…», «Sin novedades esta semana.» si no hay nada, o el mensaje del error con el botón «Generar resumen» (la API responde 503 con el código `WeeklySummary.Unavailable` si la IA no está configurada o falla). **Verificado en un Chrome real contra la API real y PostgreSQL** (error 503 con la IA apagada y un clic en «Generar resumen» que pide una vez más, semana sin novedades real, y con las respuestas simuladas en el navegador: tres frases sin la línea en blanco, semana vacía, un 409 que se repite solo una vez y dos 409 seguidos que acaban en el error). En desarrollo, `StrictMode` monta el efecto dos veces y por tanto la primera apertura pide el resumen dos veces; en producción solo una.
- **Mi perfil (`pages/Profile.tsx`, ruta `/more/profile`, enlazada desde «Más»)**: tres tarjetas. (1) «Mis datos» (`ProfileNameForm`): nombre completo editable (`IUserRepository.changeName` → `PUT /users/me`) y correo de solo lectura; al guardar, `NSwagUserRepository.changeName` actualiza el nombre de la sesión en `tokenStore` (así `useAuth().user` lo refleja), el formulario reescribe `sumiclas-guardian` con `toGuardianDisplayName` (nombre y primer apellido; conserva el rol) y llama a `ChildProvider.refresh()`. (2) «Cambiar contraseña» (`ProfilePasswordForm`): actual, nueva y repetición (mínimo `MIN_PASSWORD_LENGTH`, máximo `MAX_PASSWORD_LENGTH`, coincidencia en cliente); la contraseña actual incorrecta llega como 400 `User.CurrentPasswordInvalid` y se muestra en línea. En el 204 el servidor ya revocó **todas** las sesiones (la cookie de refresco también), así que se llama a `useAuth().signOutLocally()` (vacía `tokenStore` y los datos del tutor sin llamar a `/auth/logout`) justo después de `navigate('/login', { replace: true, state: { notice: PASSWORD_CHANGED_NOTICE } })` en el mismo tick (React los agrupa y `RequireSession` no redirige antes, perdiendo el aviso); `Login` muestra `location.state.notice` una sola vez. (3) «Mis hijos» (`ProfileChildrenSection` + `ChildNameModal`): lista de `ChildContext.children` con «Editar»; el modal guarda con `IStudentRepository.changeName` (`PUT /students/{id}`) y después `refresh()` del `ChildProvider`, de modo que `ChildSelector` y el dashboard muestran el nombre nuevo sin recargar. **Limitación conocida**: `GET /users/me/students` solo devuelve nombre e inicial del apellido, así que el modal precarga el nombre pero los apellidos hay que escribirlos de nuevo (el aviso del modal lo explica); el resto de pantallas siguen mostrando nombre + inicial. `ChildContext` expone también `currentUserName` y `currentUserEmail`. Sin verificación visual en navegador ni tests de frontend.
- **Rol en la clase (`pages/MyClassRole.tsx`, `hooks/useClassRepresentatives.ts`)**: la página lista los delegados y las familias de la clase del hijo seleccionado con `useClassMembers`; el delegado ve «Hacer delegado/a», «Ceder el rol» y «Renunciar como delegado/a» (`assignClassRepresentative` / `resignClassRepresentative` de `IUserRepository`). **No hay traspaso atómico** en la API: «Ceder el rol» es nombrar a la otra persona y después renunciar (dos llamadas); si la renuncia falla, la otra persona ya es delegada, la UI lo dice y «Reintentar la renuncia» envía solo el `DELETE`. Máximo 3 delegados (`MAX_CLASS_REPRESENTATIVES` en `lib/roles.ts`, reflejado en el cliente: con 3 se desactivan nombrar y ceder) y el único delegado no puede renunciar (la API responde 400). Ceder y renunciar piden confirmación inline (`RepresentativeConfirm`). Tras cada acción se recargan los miembros y se llama a `refresh()` del contexto. Al renunciar, la BBDD conserva una fila de `UserClassRoles` con rol `Participant`. Un hijo sin clase muestra un mensaje y no hace peticiones. **Verificado** en un Chrome real contra la API real (64 comprobaciones: nombrar, ceder en dos llamadas, límite de 3, único delegado, renuncia, fallo parcial con reintento, sin red, 403 de un ajeno, cambio de hijo con petición en vuelo, privacidad del payload y modo oscuro). **Limitaciones conocidas**: tras un fallo de red o un 5xx en el paso de renunciar, la renuncia puede haberse hecho en el servidor aunque el mensaje diga que sigues siendo delegado/a, y cerrar ese aviso también elimina el botón de reintento; «Ceder el rol» no está disponible con 3 delegados porque el paso de nombrar lo rechaza el backend (haría falta un traspaso atómico).
