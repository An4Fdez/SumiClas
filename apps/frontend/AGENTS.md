# AGENTS.md — Frontend (SumiClas)

Aplica a `apps/frontend/sumiclas-web/**`. Ver también el `AGENTS.md` de la raíz (convenciones comunes de idioma, commits, ramas y qué no tocar sin permiso).

## Stack (decisión definitiva, no una desviación temporal)

Vite + React 18 + TypeScript + Tailwind CSS v3.4 + React Router v7. El documento de arquitectura (`docs/arquitectura-app-coordinacion-escolar.md`) recomendaba React + Next.js como PWA; **esa recomendación queda descartada para el frontend real**: Vite + React es el stack oficial, confirmado con el usuario. No propongas migrar a Next.js, añadir SSR ni configurar PWA/service worker por iniciativa propia.

El frontend se está conectando al backend por tareas (plan en `odd/tasks/frontend-api-integration.md`): el registro, el perfil del usuario, sus alumnos, el onboarding y los avisos ya usan la API real; el resto de pantallas siguen con mocks de `src/data/*.ts` hasta que se migren. Ver la sección "Datos y backend real" más abajo.

## Idioma del código (cambio reciente, aplica retroactivamente)

A partir de esta decisión, **todo el código va en inglés**: nombres de archivo, componentes, carpetas, variables, tipos, props, comentarios. Esto aplica también a lo ya construido — el código existente se está renombrando/traduciendo, no solo el nuevo. Lo único que sigue en español es: el texto que ve el usuario final de la app (labels, botones, mensajes en la UI, porque los usuarios reales son hispanohablantes), los mensajes de commit, y los `AGENTS.md`/`README`.

Para traducir términos de negocio de forma consistente (y coherente con el backend), usa el glosario en `docs/glosario-dominio.md`. Si aparece un término nuevo que no está ahí, tradúcelo con el mismo criterio y añádelo a ese archivo, no lo dupliques aquí.

## Estructura de `src/`

```
src/
  components/
    app/          → componentes de UI de una pantalla/feature concreta (formularios, modales, tarjetas, desplegables). Se queda plano, sin subcarpetas por módulo.
    layout/        → AppLayout, Navbar, Reveal — armazón de la aplicación
    landing/        → secciones de la página pública (Home)
    onboarding/       → pasos del flujo de alta (colegio/clase/alumno)
  context/         → Contextos de React (ej. ChildContext.ts + ChildProvider.tsx: split definición/provider)
  data/           → datos mock + tipos (se sustituye módulo a módulo por modules/<module>/, ver más abajo)
  hooks/           → hooks reutilizables (useTheme, useChildContext...)
  lib/            → utilidades sin estado (date.ts, auth.ts, roles.ts, colorClasses.ts)
  pages/           → componentes de página, uno por ruta de React Router (Announcements.tsx, Calendar.tsx, Homework.tsx, Expenses.tsx, LostAndFound.tsx...)
  modules/
    <module>/      → capa de datos de un módulo (announcements, calendar, homework, expenses, lostAndFound...), sin UI
      domain/       → un fichero por tipo (nombre del fichero = nombre del tipo): el contrato `I<Entidad>Repository.ts` (solo la interfaz) y sus tipos de dominio (`LostItem.ts`, `NewLostItem.ts`...)
      infrastructure/ → implementación concreta del repositorio (usa el cliente compartido de modules/Shared/Infrastructure)
  modules/Shared/domain/  → tipos de dominio compartidos entre módulos (p. ej. `PageRequest.ts`)
  modules/Shared/Infrastructure/  → cliente HTTP generado con NSwag (GeneratedApiClient.ts, configuración .nswag y ClientBase.ts) más el plumbing propio (ApiClient.ts, apiDate.ts); compartido por todos los módulos, ver más abajo
```

`components/app/` no se reorganiza por módulo: la UI (formularios, tarjetas, modales) se queda donde está hoy. Solo la capa de datos (sin UI) vive en `modules/<module>/`, como carpeta de primer nivel — no anidada dentro de `components/`, porque `Domain`/`Infrastructure` no son componentes React. Esto además mantiene el frontend consistente con la estructura del backend (`SumiClas/<Module>/{Domain,Application,Infrastructure}` también como carpetas de primer nivel).

**Sin capa de Application en el frontend** (a diferencia del backend): aquí no hay lógica de negocio que justifique una capa de aplicación propia. El reparto de responsabilidades es:
- **UI (`components/app/`, `pages/`)**: comprobaciones ligeras orientadas a experiencia de usuario (campos obligatorios, formato, etc.) directamente en el formulario/pantalla — no hace falta una capa intermedia para esto.
- **Backend (`Domain` de cada módulo)**: las comprobaciones de negocio que de verdad importan (autoritativas) — nunca confíes solo en la validación del frontend.

No añadas una carpeta `application/` en `modules/<module>/` sin que se pida explícitamente; no es un olvido, es la arquitectura acordada.

## Datos y backend real

- **Hoy**: ya usan la API real el registro, el perfil del usuario y sus alumnos (`ChildProvider`). El onboarding (colegio, curso escolar, clase, alumno y matrícula), los avisos, los objetos perdidos y el calendario también usan la API real. Los deberes (con sus asignaturas) también usan la API real. Los gastos también usan la API real, con la lista de miembros de la clase para elegir participantes (**verificado en un Chrome real contra la API real y PostgreSQL, 72 comprobaciones**). Sigue con mocks en `src/data/*.ts` el resumen del dashboard (`aiSummaryByChild`).
- **Cliente HTTP**: generado por **NSwag** a partir del OpenAPI del backend (`/openapi/v1.json`, solo en Development). Vive en `src/modules/Shared/Infrastructure` (`GeneratedApiClient.ts` + `GeneratedApiClient.nswag` + `ClientBase.ts`) y es compartido por todos los módulos. No escribas `fetch`/`axios` a mano contra los endpoints — usa el cliente NSwag. Hoy el cliente generado **se comitea** y se regenera con `pnpm generate:client` (levanta una API temporal con el código actual, necesita PostgreSQL arriba; ver `Readme.md`). No se edita `GeneratedApiClient.ts` a mano.
- **Plumbing del cliente (`ApiClient.ts`, `apiDate.ts`)**: `createApiClient()` construye el cliente con `baseUrl` **`/api`** (sin barra final: el cliente concatena `baseUrl + "/ruta"`). En desarrollo, Vite reenvía `/api` a la API **quitando el prefijo** (`vite.config.ts`: destino `API_PROXY_TARGET`, por defecto `https://localhost:7064`, `secure: false` por el certificado de desarrollo). El navegador solo habla con el origen de Vite, así que hoy no hace falta CORS. El cliente se obtiene con `useApiClient()` (`ApiClientProvider` en `main.tsx`); no instancies `GeneratedApiClient` a mano.
- **Identidad provisional**: la API no tiene login; identifica al usuario por la cabecera `X-User-Id`. El cliente la envía en cada petición si hay un id guardado (`getUserId()` / `setUserId()` en `src/lib/auth.ts`, clave `sumiclas-user-id`), leyéndolo en el momento de la petición. El registro genera el id en el cliente (`crypto.randomUUID()`). La página de Login no es funcional hasta que haya autenticación real, y la contraseña no se envía a ningún sitio. Cuando llegue JWT, el único sitio a cambiar es el `identityHttp` de `ApiClient.ts` (`Authorization: Bearer`). Pendientes anotados en el `AGENTS.md` del backend: CORS y JWT.
- **Fechas**: los DTO generados tipan las fechas como `Date` pero `JSON.parse` deja texto. `ApiClient` sobrescribe `jsonParseReviver` y convierte solo las claves conocidas (`createdAt` como fecha-hora; `dueDate`, `date`, `startDate`, `endDate` como fecha sin hora, a medianoche **local** para que no cambie de día con la zona horaria); un texto libre con forma de fecha no se toca. Al **enviar** un campo de solo fecha, envuélvelo con `toApiDateOnly(date)`: la API espera `yyyy-MM-dd` y un `Date` normal se serializa como fecha-hora UTC. Si el DTO generado añade otra clave de fecha, añádela a las listas de `ApiClient.ts`.
- **Errores del cliente generado**: cuando la respuesta de error trae cuerpo (los 400, 401, 403, 404 y 409 de la API lo traen), el cliente **lanza el propio objeto `ProblemDetails`** (con `status`, `title` y el `code` del error de dominio), **no** una `ApiException`. `ApiException` solo se lanza para respuestas sin cuerpo o con un estado no declarado. Quien capture errores debe tratar ambos casos.
- **Mensajes de error en la UI**: `getApiErrorMessage(error)` (`src/lib/apiError.ts`) convierte lo que lanza el cliente (`ProblemDetails` con `code`, `ApiException` o el `TypeError` de un fallo de red) en un mensaje en español: usa el texto propio de los códigos conocidos (`User.EmailAlreadyRegistered`...), el `detail` en español de los demás errores de dominio y, si no hay, uno genérico por estado. `getApiErrorStatus(error)` devuelve el estado HTTP.
- **Repositorios ya creados**: `modules/users` (`IUserRepository`: `register`, `getCurrent`, `listClassMembers`), `modules/students` (`IStudentRepository`: `listMine`, `register`) y, para el onboarding, `modules/schools` (`ISchoolRepository`: `searchByName`, `register`), `modules/schoolYears` (`ISchoolYearRepository`: `listActive`, `create`), `modules/classes` (`IClassRepository`: `listBySchoolYear`, `create`) y `modules/enrollments` (`IEnrollmentRepository`: `create`), cada uno con su implementación `*Http`. Los cuatro del onboarding se inyectan juntos con `OnboardingRepositoriesProvider` y `useOnboardingRepositories()`. Se inyectan con `UserRepositoryProvider` y `StudentRepositoryProvider` (montados en `main.tsx`, dentro de `ApiClientProvider`) y se usan con `useUserRepository()` y `useStudentRepository()`. La capa `infrastructure` traduce los enums de la API (PascalCase) a los de la UI (`ClassRepresentative` → `classRepresentative`) y los `null` de la API a `undefined`.
- **Sesión**: `isAuthenticated()` significa que hay un id de usuario guardado, y `clearSession()` cierra la sesión (borra el id y los datos del tutor). `RequireSession` redirige a `/login` en las rutas privadas (todo `AppLayout` y `/onboarding`). La página de **Login** no es funcional: muestra un aviso en español y tiene el formulario desactivado; si ya hay sesión, redirige a `/home`. El **Registro** genera el id (`crypto.randomUUID()`), llama a `userRepository.register`, guarda el id y el rol de tutor (`sumiclas-guardian`, lo necesitará el alta de alumno) y sigue a `/onboarding`; la contraseña se valida en el formulario pero no se envía ni se guarda; un email repetido muestra el error en español y deja el formulario usable.
- **`ChildProvider`**: al montarse carga `studentRepository.listMine()` y `userRepository.getCurrent()`, y expone `loading`, `error`, `errorStatus` y `reload`; `AppLayout` muestra "Cargando tu información…" o el error con "Reintentar" y "Cerrar sesión" (necesario si el id guardado ya no existe en la API: responde 404). `currentRole` sale de `classRoles` buscando el `classId` del hijo (sin clase, `null`). Un hijo sin matrícula confirmada en un curso activo se muestra como "Sin clase". El nombre del alumno es `firstName + surnameInitial`: la API ya manda la inicial con su punto ("P."), no se añade otro. Siguen provisionales hasta T4: `currentSummary` (contadores a cero), `otherGuardians` (vacío) y las acciones de delegados (no hacen nada), porque la API no tiene resumen del dashboard y el listado de miembros de clase (`GET /classes/{classId}/members`, ya en la API y en el cliente) todavía no alimenta `otherGuardians` ni las acciones de delegado: eso es T4.6, que reutilizará `useClassMembers`. El contexto expone además `currentUserId` (el id del perfil que `ChildProvider` ya carga), que los gastos usan para saber qué participación es la tuya.
- **Onboarding (`pages/Onboarding.tsx` + `components/onboarding/*`)**: (1) colegio: `schoolFinderByName` y, si no existe, `schoolRegister` (el API exige el código oficial; no tiene ciudad). (2) clase: `useSchoolClasses` busca el curso escolar **activo** del colegio y, si no hay, crea el actual (`lib/schoolYear.ts`: del 1 de septiembre al 30 de junio; si el mes es septiembre o posterior empieza este año natural, si no el anterior) y lista sus clases; crear una clase deja al creador como delegado (lo hace el servidor). (3) alumno: `studentRegister` (el primer tutor es el usuario actual) y `enrollmentCreate`, que ya crea la matrícula **confirmada** (no hace falta `enrollmentConfirm`; comprobado en PostgreSQL). **Ids**: los genera el cliente y un id repetido da error en el backend (comprobado con una clase cuya respuesta se perdió: 409 `conflicto`, sin duplicados; en otras entidades puede ser un 500), por eso `useWizardIds` reutiliza el id de un intento fallido (`take`) y lo descarta al tener éxito (`consume`), y el asistente guarda el alumno ya registrado para que un reintento solo repita la matrícula. **Verificado** en un Chrome real contra la API real (alta de colegio, curso escolar automático sin duplicados, clase con delegado, unirse a una clase existente como participante, reintentos sin duplicados y privacidad de apellidos). El backend permite dos colegios con el mismo código oficial o el mismo nombre y el asistente no avisa. **Hueco conocido**: ya no se ofrece "unirse como segundo tutor" ni se detectan alumnos duplicados, porque la API no tiene un endpoint para listar los alumnos de una clase y `studentGuardianAdd` exige ser ya tutor del alumno.
- **Avisos (`pages/Announcements.tsx`, `modules/announcements`)**: `IAnnouncementRepository` (`listByClass`, `create`, `markAsRead`) se inyecta con `AnnouncementRepositoryProvider` y `useAnnouncementRepository()`; `useClassAnnouncements(classId)` carga la primera página de la clase del hijo seleccionado (la API devuelve juntos los avisos del colegio y los de la clase, del más reciente al más antiguo), pide más con el cursor (`Cargar más`, sin duplicados) y marca como leído de forma optimista (`PUT /read`, que revierte si falla). **El orden es el de la API**: no se reordena por prioridad en el cliente (no es compatible con la paginación por cursor); los filtros (colegio/clase, urgentes, leídos/no leídos) actúan sobre lo ya cargado. El estado de lectura es del servidor: ya no existe "marcar como no leído". Un hijo sin clase muestra un mensaje y **no hace ninguna petición**. Solo el delegado (`currentRole === 'classRepresentative'`) ve "Nuevo", y solo se ofrece ámbito de clase (los avisos oficiales de colegio son del rol de administrador del colegio, que no existe aún). El id del aviso lo genera el cliente con `useWizardIds`: se conserva tras un fallo de red o 5xx y se descarta tras el éxito o un 4xx definitivo. El selector de evento relacionado está oculto hasta migrar el calendario (T4.3), pero el aviso que ya traiga `relatedEvent` lo muestra. Verificado en un Chrome real contra la API real (27 comprobaciones: crear, leído, paginación con 25 avisos, otra clase sin fugas, hijo sin clase, reintento tras fallo de red y modo oscuro).
- **Objetos perdidos (`pages/LostAndFound.tsx`, `modules/lostItems`)**: `ILostItemRepository` (`listByClass`, `create`, `markAsRecovered`, `markAsNotRecovered`) con `NSwagLostItemRepository`, inyectado con `LostItemRepositoryProvider` y `useLostItemRepository()` (en `main.tsx`). `useClassLostItems(classId)` carga la primera página de la clase del hijo seleccionado y, con "Cargar más", las siguientes por cursor (sin duplicados); una **generación** (`generation`) se invalida al cambiar de clase o recargar, así que una respuesta o un error tardío de la clase anterior nunca llega a la nueva, y al cambiar de clase se reinician "cargando más" y su error. El estado **recuperado es del servidor y reversible**: `setRecovered(id, true|false)` llama a `markAsRecovered` o `markAsNotRecovered` con actualización optimista que se revierte (con mensaje en español) si falla. Los filtros de la página (alcance y estado) solo actúan sobre lo ya cargado, y si hay más páginas el mensaje de lista vacía lo dice. **Solo se crea con ámbito de clase** (lo de todo el colegio es del rol de administrador del colegio, que no existe) y el botón "Nuevo" solo sale si el hijo tiene clase. **Ids**: el de un intento fallido se conserva ante un fallo de red, 5xx, 408 o 429 y se descarta tras éxito o un 4xx definitivo; un 409 recarga la lista y avisa con `UserFacingError`. **Fotos (hueco conocido)**: la API solo guarda una URL (`photoUrl`, máx. 2048) y no hay endpoint para subir la imagen; la interfaz usaba URLs `blob:` locales que otros usuarios no pueden abrir, así que **se ocultó el campo de foto y nunca se envía `photoUrl`** (siempre `photoPrivacyConfirmed: false`); si la API devuelve un objeto con `photoUrl` se muestra. Habrá que decidir cómo subir imágenes antes de volver a ofrecerlo. **Hueco del backend**: repetir el id de un objeto ya guardado (respuesta perdida y reintento) responde **500** en vez de 409 (comprobado), así que el aviso del 409 solo se vería cuando el backend lo arregle.
- **Calendario (`pages/Calendar.tsx`, `modules/calendarEvents`)**: `ICalendarEventRepository` (`listByClass`, `create`, `createBirthday`) con `NSwagCalendarEventRepository`, inyectado con `CalendarEventRepositoryProvider` y `useCalendarEventRepository()` (en `main.tsx`). `useClassCalendarEvents(classId)` carga **todos** los eventos de la clase del hijo seleccionado (los del colegio, los puntuales de la clase y los cumpleaños de sus alumnos; la API no pagina ni filtra por mes, así que mes/semana/lista y los filtros son del cliente) con la misma guarda de generación que los demás hooks. Un evento tiene `month`, `day` y `year?`: **un cumpleaños no tiene año** (se repite cada año y nunca se guarda el año de nacimiento), uno puntual sí. `lib/date.ts` ya no usa el año centinela de 1900: `occurrenceInYear`, `eventOccursOnDay`, `nextOccurrence` y `visibleYearForEvent` reciben `{ month, day, year? }`, y un 29 de febrero recurrente cae el **28 de febrero** en los años no bisiestos. `eventTypeMeta` vive en `lib/eventTypeMeta.ts`. Al crear: solo ámbito de clase (los eventos de todo el colegio son del administrador del colegio, que no existe como rol); el delegado ve el selector de tipo y cualquier tutor ve solo el formulario de cumpleaños de **su** hijo (el título se construye con `studentName`); la fecha se envía con `toApiDateOnly` y la hora como `HH:mm` (la API la devuelve como `HH:mm:ss` y el repositorio la recorta); el id se guarda por clase y contenido exacto (otro contenido recibe otro id), se conserva ante fallo de red, 5xx, 408 y 429 y se descarta tras éxito o un 4xx; un 409 recarga y avisa. El selector de **evento relacionado** de los avisos vuelve a estar activo con los próximos eventos puntuales de la clase (sin cumpleaños). **Verificado** en un Chrome real contra la API real, incluidas las zonas UTC+14 y UTC-8 sin desfase de día.
- **Deberes (`pages/Homework.tsx`, `modules/assignments`, `modules/subjects`)**: `IAssignmentRepository` (`listByClass`, `create`, `addComment`) con `NSwagAssignmentRepository` y `ISubjectRepository` (`listByClass`, `create`) con `NSwagSubjectRepository`, inyectados juntos con `HomeworkRepositoriesProvider` y `useHomeworkRepositories()` (en `main.tsx`). `useClassAssignments(classId)` carga la primera página (la API ordena por fecha de entrega ascendente y trae los comentarios dentro de cada tarea), pagina con «Cargar más» y descarta las respuestas y errores tardíos de otra clase (generación) también al cambiar de hijo; `useClassSubjects(classId)` carga las asignaturas. Un hijo sin clase muestra un mensaje y no hace peticiones. **Asignaturas**: la API solo tiene `{id, classId, label}` y **no hay catálogo por defecto**; solo el delegado de la clase las crea (en el formulario, «Añadir asignatura»), y un participante de una clase sin asignaturas ve que el delegado tiene que crearlas antes y no puede proponer. El color de una asignatura no existe en la API: sale de un hash estable de su id (`lib/subjectColor.ts`), no de su posición en la lista. **Oficial o propuesta**: lo decide el servidor (`isProposal`, `false` si quien crea es delegado de esa clase); la UI solo muestra la insignia «Propuesta». **No hay endpoint para aprobar** una propuesta, así que la UI no ofrece aprobarla. **Comentarios**: `addComment` crea el comentario con el usuario actual; se añade de forma optimista y se revierte con un mensaje en español si falla. **«Hecho»**: la API no guarda ese estado, así que es una marca solo del dispositivo en `localStorage` (`sumiclas-homework-done:<userId>`, lista de ids de tareas; `hooks/useDoneAssignments.ts`) y no se sincroniza entre dispositivos. **Fechas**: la fecha de entrega es solo fecha (medianoche local) y se envía con `toApiDateOnly`; las etiquetas salen de `formatDueDate` y `formatDayHeading` (`lib/date.ts`). **Ids de creación**: ligados a la clase y al contenido exacto del formulario (`assignment:<classId>:<json>`), se conservan ante fallo de red, 5xx, 408 y 429 y se descartan tras éxito o un 4xx definitivo; un 409 recarga la lista y avisa con `UserFacingError`. Los filtros de asignatura y de pendientes/hechas solo actúan sobre lo ya cargado y el mensaje de lista vacía lo dice cuando hay más páginas. **Verificado** en un Chrome real contra la API real (asignaturas, tarea oficial y propuesta, fechas sin desfase en tres husos horarios, comentarios con reversión, paginación con 29 tareas, otra clase, hijo sin clase, fallo de red al crear, respuestas tardías al cambiar de hijo y modo oscuro).
- **Gastos (`pages/Expenses.tsx`, `modules/classExpenses`)**: `IClassExpenseRepository` (`listByClass`, `create`, `markAsPaid`, `markAsUnpaid`) con `NSwagClassExpenseRepository`, inyectado con `ClassExpenseRepositoryProvider` y `useClassExpenseRepository()` (en `main.tsx`). `useClassExpenses(classId)` carga la primera página de la clase del hijo seleccionado (más recientes primero; cada gasto trae sus participantes con `hasPaid`), pagina con «Cargar más» y descarta las respuestas y errores tardíos de otra clase (generación). Un hijo sin clase muestra un mensaje y no hace peticiones. **Quién paga**: cada participante marca o desmarca **solo su propio** pago (`PUT`/`DELETE` de `paid`, idempotentes), con actualización optimista que se revierte con un mensaje en español si falla y un segundo clic ignorado mientras la petición sigue en curso; el backend todavía no autoriza quién marca el pago de quién. **Crear**: solo el delegado (`currentRole === 'classRepresentative'`). Los participantes se eligen de la lista de miembros de la clase (`useClassMembers`, que solo se pide mientras el formulario está abierto; un no miembro recibe un 403 que se muestra dentro del selector con «Reintentar»), por defecto todos. **Dinero**: el importe se escribe por familia y `lib/money.ts` lo convierte a **céntimos enteros** (`parseEuroAmount`), así que más de 2 decimales se rechaza en el formulario con un mensaje y el total nunca pasa por aritmética de coma flotante (`totalAmount = céntimos / 100`, máximo 99.999.999,99 €, la columna es `decimal(10,2)` y redondearía en silencio); se muestra con `Intl.NumberFormat('es-ES', EUR)` (`formatEuros`). El concepto admite 200 caracteres (límite del backend). **Evento relacionado**: `useUpcomingEventOptions(classId)` ofrece los próximos eventos puntuales de la clase (sin cumpleaños) y se envía `relatedEventId`. **Ids de creación**: ligados a la clase y al contenido exacto del formulario, se conservan ante fallo de red, 5xx, 408 y 429 y se descartan tras éxito o un 4xx definitivo; un 409 recarga y avisa con `UserFacingError`. Los filtros «Pendientes/Pagados» solo actúan sobre lo ya cargado y el mensaje de lista vacía lo dice cuando hay más páginas. Un rol de autor desconocido queda `undefined` (`parseClassRole` en `lib/roles.ts`) en vez de convertirse en participante. **Estado**: verificado contra la API real y PostgreSQL con un Chrome headless (72 comprobaciones: crear con participantes reales, céntimos, pagar/desmarcar con recarga y reversión sin red, paginación con 25 gastos, aislamiento entre clases, reintento tras fallo de red con un solo gasto, cambio de hijo con petición en vuelo, 403 en el selector, evento relacionado, modo oscuro). **Límite conocido del backend**: si se pierde la respuesta de crear tras guardarse el gasto, el reintento con el mismo id devuelve 500 en vez de 409, así que la app muestra un error genérico aunque el gasto ya existe (no se duplica).
- **Patrón repositorio**, en `src/modules/<module>/`:
  - `domain/` — un fichero por tipo (nombre del fichero = nombre del tipo): el contrato del repositorio (ej. `IAnnouncementRepository`, en `domain/IAnnouncementRepository.ts`) contiene **solo la interfaz**, y cada tipo de dominio del módulo va en su propio fichero (`Announcement.ts`, `AnnouncementPage.ts`, `NewAnnouncement.ts`...). Los tipos compartidos entre módulos (p. ej. `PageRequest`) viven en `modules/Shared/domain/`. Sin ficheros índice ni reexportaciones: cada uno se importa desde su fichero. No depende de `infrastructure` ni del cliente NSwag.
  - `infrastructure/` — implementación concreta del repositorio (ej. `NSwagAnnouncementRepository`) que usa el cliente compartido de `modules/Shared/Infrastructure` para hacer las llamadas reales.
  - No se usa TanStack Query ni ninguna librería de caché de peticiones para esto.
- **Inyección de la implementación**: mediante un Contexto de React (mismo patrón que `ChildContext`/`ChildProvider`), no como singleton importado directamente ni instanciado a mano en el componente. Esto permite sustituir la implementación por un mock en los tests de `apps/test/frontend`. Componentes y hooks (en `components/app/`) consumen el repositorio a través de un hook propio (p. ej. `useAnnouncementRepository()`), nunca instanciando `NSwagAnnouncementRepository` directamente.
- Los mocks actuales de `src/data/*.ts` se sustituyen por `modules/<module>/` **módulo a módulo**, no todos a la vez.
- **Pendiente de decidir**: si el cliente NSwag generado se sigue comiteando (hoy sí) o pasa a generarse en cada build; y si los estados de carga/error de las llamadas a los repositorios, hoy a mano con `useState` (`ChildProvider`, `Register`), merecen una utilidad común cuando haya más pantallas migradas. No asumas ninguna de las dos cosas sin confirmarlo primero.

## Patrones de UI ya establecidos (síguelos, no los reinventes)

- **Modales**: `fixed inset-0 z-50 flex items-end sm:items-center justify-center bg-slate-900/40 backdrop-blur-sm` + tarjeta `rounded-t-3xl sm:rounded-3xl border border-slate-200 dark:border-slate-700 bg-white dark:bg-slate-900 shadow-xl`. Usa el truco del ref `mouseDownOnBackdrop` (solo cierra si el `mousedown` **y** el `click` caen sobre el propio fondo) para que seleccionar texto y arrastrar fuera del modal no lo cierre.
- **Desplegables/selectores personalizados**: nunca uses `<select>` nativo ni `<input type="date"/"time">` nativos — su popup no se puede estilar (bordes cuadrados, no respeta el modo oscuro). Usa/reutiliza `SelectDropdown`, `DatePicker` y `TimePicker` (`src/components/app/`), que renderizan su panel vía `createPortal` a `document.body` para no quedar recortados por el `overflow-y-auto` de un modal contenedor.
- **Filtros de página** (no dentro de modal): trigger tipo pastilla (`rounded-full`) + panel `absolute` con `onBlur` que cierra si el foco sale del contenedor (no necesitan portal al no estar dentro de un modal con scroll).
- **Estado local "activado/desactivado" sobre datos base** (leído/no leído, hecho, recuperado...): un `Set<string>` de ids "conmutados" que se aplica en XOR sobre el valor base, no dupliques el dato completo en estado local.
- **Permisos por rol**: `useChildContext()` expone `currentRole`, `children`, `currentChild`, `otherGuardians`, `setCurrentChildId`. Compara `currentRole === 'classRepresentative'` para contenido oficial vs `'participant'` para propuestas/comentarios.
- **Modo oscuro**: `useTheme` alterna la clase `dark` en `document.documentElement` (`darkMode: 'class'` en `tailwind.config.js`). Todo componente nuevo necesita sus variantes `dark:` a la par que las claras, nunca solo un tema.
- **Privacidad de menores**: nunca mostrar apellido completo (solo inicial), nunca pedir/guardar año de nacimiento (cumpleaños solo día+mes), fotos de objetos perdidos con checkbox de confirmación explícita antes de publicar.

## Nomenclatura

- Inglés en todo el código: nombres de componentes, archivos, props, hooks propios y variables (`AnnouncementForm`, `eventsForDay`, `className`, `useChildContext`). Ver `docs/glosario-dominio.md` para traducir términos de negocio de forma consistente.
- Un componente por archivo, nombre de archivo = nombre del componente en PascalCase.
- Las interfaces (contratos/puertos, p. ej. los repositorios en `domain/`) llevan prefijo `I` (`IUserRepository`) y el fichero se llama igual (`domain/IUserRepository.ts`); su implementación contra la API se llama `NSwag<Entidad>Repository` (`NSwagUserRepository`, en `infrastructure/NSwagUserRepository.ts`) porque usa el cliente generado por NSwag; si algún día otra implementación usara otra fuente, llevaría su propio prefijo. Los tipos de datos (`Child`, `Profile`) no llevan prefijo y van **un fichero por tipo en `domain/`** (nombre del fichero = nombre del tipo, p. ej. `domain/Profile.ts`): el contrato `I<Entidad>Repository.ts` contiene solo la interfaz, y los tipos compartidos entre módulos (p. ej. `PageRequest`) viven en `modules/Shared/domain/`.
- Tipos/props inline en la firma del componente (`{ prop1, prop2 }: { prop1: X; prop2: Y }`), no interfaces `Props` separadas salvo que el tipo se reutilice en más de un sitio.

## Estilo

- Tailwind utility-first en todo; no hay CSS Modules ni styled-components. No introduzcas ninguno de los dos sin acordarlo antes.
- Iconos: `lucide-react` exclusivamente.
- Sin librería de i18n: los **textos de la UI** van en español directamente en el JSX (no hay previsto soporte multi-idioma) — esto no cambia con la nueva convención de idioma del código, que solo afecta a identificadores/archivos, no al contenido renderizado.
