# AGENTS.md — Frontend (SumiClas)

Aplica a `apps/frontend/sumiclas-web/**`. Ver también el `AGENTS.md` de la raíz (convenciones comunes de idioma, commits, ramas y qué no tocar sin permiso).

## Stack (decisión definitiva, no una desviación temporal)

Vite + React 18 + TypeScript + Tailwind CSS v3.4 + React Router v7. El documento de arquitectura (`docs/arquitectura-app-coordinacion-escolar.md`) recomendaba React + Next.js como PWA; **esa recomendación queda descartada para el frontend real**: Vite + React es el stack oficial, confirmado con el usuario. No propongas migrar a Next.js, añadir SSR ni configurar PWA/service worker por iniciativa propia.

El frontend se está conectando al backend por tareas (plan en `odd/tasks/frontend-api-integration.md`): el registro, el perfil del usuario, sus alumnos, el onboarding y los avisos ya usan la API real; el resto de pantallas siguen con mocks de `src/data/*.ts` hasta que se migren. Ver la sección "Datos y backend real" más abajo.

## Idioma del código (cambio reciente, aplica retroactivamente)

A partir de esta decisión, **todo el código va en inglés**: nombres de archivo, componentes, carpetas, variables, tipos, props, comentarios. Esto aplica también a lo ya construido — el código existente se está renombrando/traduciendo, no solo el nuevo. Lo único que sigue en español es: el texto que ve el usuario final de la app (labels, botones, mensajes en la UI, porque los usuarios reales son hispanohablantes), los mensajes de commit, y los `AGENTS.md`/`README`.

Para traducir términos de negocio de forma consistente (y coherente con el backend), usa el glosario en `docs/glosario-dominio.md`. Si aparece un término nuevo que no está ahí, tradúcelo con el mismo criterio y añádelo a ese archivo, no lo dupliques aquí.

## Estructura de `src/`

```
src/
  components/
    app/          → componentes de UI de una pantalla/feature concreta (formularios, modales, tarjetas, desplegables). Se queda plano, sin subcarpetas por módulo.
    layout/        → AppLayout, Navbar, Reveal — armazón de la aplicación
    landing/        → secciones de la página pública (Home)
    onboarding/       → pasos del flujo de alta (colegio/clase/alumno)
  context/         → Contextos de React (ej. ChildContext.ts + ChildProvider.tsx: split definición/provider)
  data/           → datos mock + tipos (se sustituye módulo a módulo por modules/<module>/, ver más abajo)
  hooks/           → hooks reutilizables (useTheme, useChildContext...)
  lib/            → utilidades sin estado (date.ts, auth.ts, roles.ts, colorClasses.ts)
  pages/           → componentes de página, uno por ruta de React Router (Announcements.tsx, Calendar.tsx, Homework.tsx, Expenses.tsx, LostAndFound.tsx...)
  modules/
    <module>/      → capa de datos de un módulo (announcements, calendar, homework, expenses, lostAndFound...), sin UI
      domain/       → un fichero por tipo (nombre del fichero = nombre del tipo): el contrato `I<Entidad>Repository.ts` (solo la interfaz) y sus tipos de dominio (`LostItem.ts`, `NewLostItem.ts`...)
      infrastructure/ → implementación concreta del repositorio (usa el cliente compartido de modules/Shared/Infrastructure)
  modules/Shared/domain/  → tipos de dominio compartidos entre módulos (p. ej. `PageRequest.ts`)
  modules/Shared/Infrastructure/  → cliente HTTP generado con NSwag (GeneratedApiClient.ts, configuración .nswag y ClientBase.ts) más el plumbing propio (ApiClient.ts, apiDate.ts); compartido por todos los módulos, ver más abajo
```

`components/app/` no se reorganiza por módulo: la UI (formularios, tarjetas, modales) se queda donde está hoy. Solo la capa de datos (sin UI) vive en `modules/<module>/`, como carpeta de primer nivel — no anidada dentro de `components/`, porque `Domain`/`Infrastructure` no son componentes React. Esto además mantiene el frontend consistente con la estructura del backend (`SumiClas/<Module>/{Domain,Application,Infrastructure}` también como carpetas de primer nivel).

**Sin capa de Application en el frontend** (a diferencia del backend): aquí no hay lógica de negocio que justifique una capa de aplicación propia. El reparto de responsabilidades es:
- **UI (`components/app/`, `pages/`)**: comprobaciones ligeras orientadas a experiencia de usuario (campos obligatorios, formato, etc.) directamente en el formulario/pantalla — no hace falta una capa intermedia para esto.
- **Backend (`Domain` de cada módulo)**: las comprobaciones de negocio que de verdad importan (autoritativas) — nunca confíes solo en la validación del frontend.

No añadas una carpeta `application/` en `modules/<module>/` sin que se pida explícitamente; no es un olvido, es la arquitectura acordada.

## Datos y backend real

- **Hoy**: ya usan la API real el registro, el perfil del usuario y sus alumnos (`ChildProvider`). El onboarding (colegio, curso escolar, clase, alumno y matrícula), los avisos, los objetos perdidos y el calendario también usan la API real. Los deberes (con sus asignaturas) también usan la API real. Los gastos también usan la API real, con la lista de miembros de la clase para elegir participantes (**verificado en un Chrome real contra la API real y PostgreSQL, 72 comprobaciones**). Sigue con mocks en `src/data/*.ts` el resumen del dashboard (`aiSummaryByChild`).
- **Cliente HTTP**: generado por **NSwag** a partir del OpenAPI del backend (`/openapi/v1.json`, **protegido con Bearer incluso en Development**). Vive en `src/modules/Shared/Infrastructure` (`GeneratedApiClient.ts` + `GeneratedApiClient.nswag` + `ClientBase.ts`) y es compartido por todos los módulos. No escribas `fetch`/`axios` a mano contra los endpoints — usa el cliente NSwag. Hoy el cliente generado **se comitea** y se regenera con `pnpm generate:client` (levanta una API temporal con el código actual, necesita PostgreSQL arriba porque la API aplica las migraciones pendientes al arrancar; ver `Readme.md`). Como el documento exige Bearer, el script arranca esa API con una clave de firma propia y desechable (`Jwt__SigningKey`, aleatoria en cada ejecución, que tiene prioridad sobre los User Secrets: no lee los secretos del usuario), fabrica un JWT HS256 de 5 minutos con los `iss`/`aud` de `appsettings.json` y lo envía como `Authorization: Bearer` al descargar el documento. Con `--url` (una API ya en marcha) se pasa un token propio con `--token <jwt>` o la variable `SUMICLAS_OPENAPI_TOKEN`. No se edita `GeneratedApiClient.ts` a mano.
- **Plumbing del cliente (`ApiClient.ts`, `apiDate.ts`)**: `createApiClient()` construye el cliente con `authHttp` (ver «Sesión») y `baseUrl` **`/api`** (`API_BASE_URL`, en `authHttp.ts`) (sin barra final: el cliente concatena `baseUrl + "/ruta"`). En desarrollo, Vite reenvía `/api` a la API **quitando el prefijo** (`vite.config.ts`: destino `API_PROXY_TARGET`, por defecto `https://localhost:7064`, `secure: false` por el certificado de desarrollo). El navegador solo habla con el origen de Vite, así que hoy no hace falta CORS. El cliente se obtiene con `useApiClient()` (`ApiClientProvider` en `main.tsx`); no instancies `GeneratedApiClient` a mano.
- **Identidad y token de acceso**: la API exige `Authorization: Bearer <accessToken>` en todo salvo `/auth/*` y `/healthy`; ya no existe la cabecera `X-User-Id` (la API la ignora y el cliente no la envía). El access token (JWT de 15 minutos) vive **solo en memoria**: `src/lib/tokenStore.ts` (variables de módulo; `getAccessToken`, `getSession`, `setSession`, `clearSession` y `subscribe(listener)` para que un proveedor de React reaccione). Nunca se escribe en `localStorage`/`sessionStorage`/cookies. `src/lib/auth.ts` conserva solo los datos no sensibles del tutor (`sumiclas-guardian`: `getGuardianInfo`, `setGuardianInfo`, `clearGuardianInfo`), y expone `removeLegacySessionKeys()`, que `main.tsx` llama al arrancar para borrar las claves antiguas `sumiclas-user-id` y `sumiclas-auth` de `localStorage`. El código de React no lee `tokenStore` directamente: usa `useAuth()`. El refresh token viaja **solo** en la cookie `sumiclas_refresh` (`HttpOnly; Secure; SameSite=Strict; Path=/api/auth`) que el navegador envía por sí mismo en las llamadas a `/api/auth/*` (mismo origen, vía el proxy de Vite): el código del frontend nunca la lee.
- **Fechas**: los DTO generados tipan las fechas como `Date` pero `JSON.parse` deja texto. `ApiClient` sobrescribe `jsonParseReviver` y convierte solo las claves conocidas (`createdAt` como fecha-hora; `dueDate`, `date`, `startDate`, `endDate` como fecha sin hora, a medianoche **local** para que no cambie de día con la zona horaria); un texto libre con forma de fecha no se toca. Al **enviar** un campo de solo fecha, envuélvelo con `toApiDateOnly(date)`: la API espera `yyyy-MM-dd` y un `Date` normal se serializa como fecha-hora UTC. Si el DTO generado añade otra clave de fecha, añádela a las listas de `ApiClient.ts`.
- **Errores del cliente generado**: cuando la respuesta de error trae cuerpo (los 400, 401, 403, 404 y 409 de la API lo traen), el cliente **lanza el propio objeto `ProblemDetails`** (con `status`, `title` y el `code` del error de dominio), **no** una `ApiException`. `ApiException` solo se lanza para respuestas sin cuerpo o con un estado no declarado. Quien capture errores debe tratar ambos casos.
- **Mensajes de error en la UI**: `getApiErrorMessage(error)` (`src/lib/apiError.ts`) convierte lo que lanza el cliente (`ProblemDetails` con `code`, `ApiException` o el `TypeError` de un fallo de red) en un mensaje en español: usa el texto propio de los códigos conocidos (`User.EmailAlreadyRegistered`...), el `detail` en español de los demás errores de dominio y, si no hay, uno genérico por estado. `getApiErrorStatus(error)` devuelve el estado HTTP. El backend documenta en OpenAPI los errores 400, 401, 403, 404 y 409 de cada operación como un único `ProblemDetails` (`ProblemResponsesTransformer`), así que el cliente generado lanza `ProblemDetails` con su `code` en todos ellos; una `ApiException` solo llega para los estados no documentados, como el 500.
- **Repositorios ya creados**: `modules/sessions` (`ISessionRepository`: `login(newSession): Session`, `refresh(): Session`, `logout()`; tipos `NewSession` y `Session` (`{ accessToken, expiresAt, userId, fullName }`); `NSwagSessionRepository`, inyectado con `SessionRepositoryProvider` y `useSessionRepository()` en `main.tsx`), `modules/users` (`IUserRepository`: `getCurrent`, `listClassMembers`, `register(newUser)`; tipo `NewUser`), `modules/students` (`IStudentRepository`: `listMine`, `register`) y, para el onboarding, `modules/provinces` (`IProvinceRepository`: `listAll`), `modules/localities` (`ILocalityRepository`: `listByProvince(provinceId, name?)`), `modules/schools` (`ISchoolRepository`: `findByLocality(localityId, name?)`, `findById`; ya no existe el alta libre de colegios), `modules/schoolYears` (`ISchoolYearRepository`: `listActive`, `create`), `modules/classes` (`IClassRepository`: `listBySchoolYear`, `create`) y `modules/enrollments` (`IEnrollmentRepository`: `create`), cada uno con su implementación `*Http`. Los cuatro de colegios, cursos, clases y matrículas se inyectan juntos con `OnboardingRepositoriesProvider` y `useOnboardingRepositories()`; provincias y poblaciones tienen cada una su contexto (`ProvinceRepositoryProvider`/`useProvinceRepository()`, `LocalityRepositoryProvider`/`useLocalityRepository()`, montados en `main.tsx`). Se inyectan con `UserRepositoryProvider` y `StudentRepositoryProvider` (montados en `main.tsx`, dentro de `ApiClientProvider`) y se usan con `useUserRepository()` y `useStudentRepository()`. La capa `infrastructure` traduce los enums de la API (PascalCase) a los de la UI (`ClassRepresentative` → `classRepresentative`) y los `null` de la API a `undefined`.
- **Sesión**: `src/modules/Shared/Infrastructure/authHttp.ts` (sustituye al antiguo `identityHttp`) es el `http` del cliente generado: añade `Authorization: Bearer` si hay access token y, ante un **401** en una petición que no es de `/auth/*`, llama a `refreshSession()` **una vez** y repite la petición original **una vez** con el token nuevo (si otra petición ya renovó el token, repite sin refrescar). Un 401 de `/auth/login`, `/auth/register`, `/auth/refresh` o `/auth/logout` nunca dispara un refresco. `refreshSession()` es *single-flight* (los llamadores simultáneos comparten una sola promesa), se serializa entre pestañas con `navigator.locks.request('sumiclas-refresh', …)` cuando existe, llama a `POST /api/auth/refresh` con una instancia del cliente que **no** usa `authHttp` (sin recursión) y guarda la sesión en `tokenStore`; si responde 401 (cookie rotada por otra pestaña) o 409 (`Shared.ConcurrencyConflict`, perdió una carrera) espera 300 ms y lo reintenta **una vez**; si vuelve a fallar así, vacía la sesión en memoria, llama al callback registrado con `setSessionLostHandler(fn)` y la petición original termina con su 401. Un fallo de red, un 5xx o un 429 del refresco no se consideran sesión perdida (no se llama al callback). Los nombres del cliente generado son `userRegister`, `sessionCreate` (login), `sessionRotate` (`POST /auth/refresh`) y `sessionRevoke` (`POST /auth/logout`); `NSwagSessionRepository` guarda la sesión en `tokenStore` al hacer login o refresh (`refresh()` comparte el *single-flight* y el *lock* de `refreshSession`, sin llamar al callback) y la vacía en `logout()` aunque la llamada falle. Los errores nuevos tienen mensaje en español en `apiError.ts` (`Authentication.RefreshTokenInvalid`, `Authentication.Unauthenticated`, `Shared.ConcurrencyConflict`). **Estado de la sesión en React (`AuthProvider`/`useAuth`)**: `src/context/AuthProvider.tsx` (con `AuthContext.ts` y `useAuth()` en `src/hooks/useAuth.ts`) se monta en `main.tsx` **dentro de `BrowserRouter`** y debajo de `SessionRepositoryProvider`/`UserRepositoryProvider`, y expone `status` (`'loading' | 'authenticated' | 'anonymous'`), `user` (`{ userId, fullName }` o `null`) y las acciones `login(newSession)`, `register(newUser)` y `logout()`. **Arranque**: la primera renderización ya no espera a la red; al montarse, el proveedor llama **una vez** a `sessionRepository.refresh()` (RF-18) para restaurar la sesión desde la cookie (con una bandera `ignore` por si StrictMode ejecuta el efecto dos veces; el *single-flight* de `authHttp` evita dos peticiones) y mientras tanto el estado es `loading`; si responde, `authenticated`, y si falla, `anonymous`. Se suscribe a `tokenStore.subscribe`, así que el estado sigue a la sesión en memoria. **Sesión perdida**: registra `setSessionLostHandler` (y lo quita al desmontarse); cuando un refresco es rechazado se actualiza el estado a `anonymous` y se navega a `/login` con `replace`. **`RequireSession`** (`components/layout/RequireSession.tsx`): `loading` muestra `SessionLoading` (`role="status"`, «Cargando tu sesión…») sin redirigir; `anonymous` redirige a `/login` con `replace`; `authenticated` renderiza el `Outlet`. `Login` también espera a que termine `loading` antes de redirigir a `/home` a quien ya tiene sesión. **Registro**: `useAuth().register` hace `userRepository.register` y después `sessionRepository.login` con las mismas credenciales (RF-20); si solo falla el login posterior lanza `AccountCreatedLoginFailedError` (con `loginError`) y `Register` muestra «Tu cuenta se ha creado, pero…», conservando la política de ids y el 409. **Un único cierre de sesión**: `useAuth().logout()` llama a `sessionRepository.logout()` ignorando su error (el repositorio ya vacía la sesión local), borra los datos del tutor (`clearGuardianInfo`) y deja el estado `anonymous`; nunca lanza. `More` y `AppLayout` lo esperan y navegan a `/login` con `replace` (el botón Atrás no reentra en rutas privadas). El rol de tutor sigue sin recuperarse en el login (se guarda `guardian`) y el enlace «¿La olvidaste?» apunta a `/forgot-password`, que no existe. **Verificación**: la lógica de `authHttp`/`refreshSession` se comprobó con un `fetch` simulado (peticiones simultáneas, 401 de `/auth/*`, reintento a los 300 ms, 409, sin `navigator.locks`); los escenarios S-21..S-28 de extremo a extremo en un navegador real son de J4.
- **`ChildProvider`**: al montarse carga `studentRepository.listMine()` y `userRepository.getCurrent()`, y expone `loading`, `error`, `errorStatus` y `reload`; `AppLayout` muestra "Cargando tu información…" o el error con "Reintentar" y "Cerrar sesión" (necesario si el usuario de la sesión ya no existe en la API: responde 404). `currentRole` sale de `classRoles` buscando el `classId` del hijo (sin clase, `null`). Un hijo sin matrícula confirmada en un curso activo se muestra como "Sin clase". El nombre del alumno es `firstName + surnameInitial`: la API ya manda la inicial con su punto ("P."), no se añade otro. Sigue provisional `currentSummary` (contadores a cero), porque la API no tiene resumen del dashboard. El contexto expone `refresh()`, que recarga alumnos y perfil **sin** mostrar la pantalla de carga y, si falla, deja en pantalla los datos que ya había (lo usa la gestión de delegados para actualizar el rol tras nombrar o renunciar). El contexto expone además `currentUserId` (el id del perfil que `ChildProvider` ya carga), que los gastos usan para saber qué participación es la tuya. **Limitación conocida**: `refresh()` no secuencia ni cancela peticiones, así que dos refrescos que se solapan, o uno junto a un `reload`, pueden terminar fuera de orden y devolver un `currentRole` antiguo; uno que llega mientras se está cargando se descarta.
- **Onboarding (`pages/Onboarding.tsx` + `components/onboarding/*`)**: (1) colegio: provincia -> población -> colegio. `useProvinces` carga las 52 provincias; `useProvinceLocalities(provinceId)` carga **todas** las poblaciones de la provincia (la API no pagina; la mayor tiene 299) y `useLocalitySchools(localityId, name)` pide `schoolFinderByLocality` con el nombre con debounce de 300 ms (la API devuelve como mucho 50 colegios y el filtro ignora tildes y mayúsculas); los tres usan una guarda de generación para descartar respuestas y errores tardíos. Cambiar de provincia reinicia población y búsqueda; cambiar de población reinicia solo la búsqueda. Provincia y población usan `components/app/SearchableSelect.tsx` (campo con filtro en el cliente sin tildes, máximo 100 opciones visibles; se eligió en vez de `SelectDropdown`, que no tiene filtro, y de un `<select>` nativo, prohibido por el diseño) y los resultados muestran nombre, dirección, código postal y población y teléfono. **No existe alta de colegios**: solo se eligen los del catálogo oficial, y se quitaron el formulario, el caso de uso y el id `school` del asistente. (2) clase: `useSchoolClasses` busca el curso escolar **activo** del colegio y, si no hay, crea el actual (`lib/schoolYear.ts`: del 1 de septiembre al 30 de junio; si el mes es septiembre o posterior empieza este año natural, si no el anterior) y lista sus clases; crear una clase deja al creador como delegado (lo hace el servidor). (3) alumno: `studentRegister` (el primer tutor es el usuario actual) y `enrollmentCreate`, que ya crea la matrícula **confirmada** (no hace falta `enrollmentConfirm`; comprobado en PostgreSQL). **Ids**: los genera el cliente y un id repetido da error en el backend (comprobado con una clase cuya respuesta se perdió: 409 `conflicto`, sin duplicados; el backend responde 409 también en las demás entidades), por eso `useWizardIds` reutiliza el id de un intento fallido (`take`) y lo descarta al tener éxito (`consume`), y el asistente guarda el alumno ya registrado para que un reintento solo repita la matrícula. **Limitación conocida**: tras un 409, los pasos de colegio, alumno y matrícula conservan el mismo id del asistente, así que si la respuesta se perdió después de guardarse, cada reintento vuelve a dar 409 (el colegio ya no se crea, así que no cuenta); solo la creación de la clase descarta el id y recarga la lista. Habría que tratar ese 409 como «ya creado» y continuar con lo guardado. **Verificado** en un Chrome real contra la API real (alta de colegio, curso escolar automático sin duplicados, clase con delegado, unirse a una clase existente como participante, reintentos sin duplicados y privacidad de apellidos). **Hueco conocido**: ya no se ofrece "unirse como segundo tutor" ni se detectan alumnos duplicados, porque la API no tiene un endpoint para listar los alumnos de una clase y `studentGuardianAdd` exige ser ya tutor del alumno.
- **Avisos (`pages/Announcements.tsx`, `modules/announcements`)**: `IAnnouncementRepository` (`listByClass`, `create`, `markAsRead`) se inyecta con `AnnouncementRepositoryProvider` y `useAnnouncementRepository()`; `useClassAnnouncements(classId)` carga la primera página de la clase del hijo seleccionado (la API devuelve juntos los avisos del colegio y los de la clase, del más reciente al más antiguo), pide más con el cursor (`Cargar más`, sin duplicados) y marca como leído de forma optimista (`PUT /read`, que revierte si falla). **El orden es el de la API**: no se reordena por prioridad en el cliente (no es compatible con la paginación por cursor); los filtros (colegio/clase, urgentes, leídos/no leídos) actúan sobre lo ya cargado. El estado de lectura es del servidor: ya no existe "marcar como no leído". Un hijo sin clase muestra un mensaje y **no hace ninguna petición**. Solo el delegado (`currentRole === 'classRepresentative'`) ve "Nuevo", y solo se ofrece ámbito de clase (los avisos oficiales de colegio son del rol de administrador del colegio, que no existe aún). El id del aviso lo genera el cliente con `useWizardIds`: se conserva tras un fallo de red o 5xx y se descarta tras el éxito o un 4xx definitivo. El selector de evento relacionado está oculto hasta migrar el calendario (T4.3), pero el aviso que ya traiga `relatedEvent` lo muestra. Verificado en un Chrome real contra la API real (27 comprobaciones: crear, leído, paginación con 25 avisos, otra clase sin fugas, hijo sin clase, reintento tras fallo de red y modo oscuro).
- **Ámbito colegio cerrado en esta versión** (decisión del usuario, 2026-10-23): el backend rechaza publicar avisos, eventos y objetos perdidos con ámbito colegio (403 `User.SchoolPublishForbidden`; ver "Ámbito colegio" en `apps/backend/AGENTS.md`) hasta que existan los roles de admin del colegio y de profesor. Los formularios no ofrecen ese ámbito (crean siempre con `scope: 'class'`) y las pantallas de avisos, calendario y objetos perdidos ya no muestran la pestaña de filtro "Colegio", que saldría siempre vacía. Se conservan los tipos `AnnouncementScope`, `EventScope` e `ItemScope` con `'school'`, las etiquetas "Colegio" de las tarjetas y el filtro por ámbito para cuando se abra. **Para abrirlo**: devolver los roles en el perfil del usuario, ofrecer el ámbito colegio en los formularios solo a quien puede publicarlo y volver a añadir `{ value: 'school', label: 'Colegio' }` a `scopeFilters` en las tres pantallas.
- **Objetos perdidos (`pages/LostAndFound.tsx`, `modules/lostItems`)**: `ILostItemRepository` (`listByClass`, `create`, `markAsRecovered`, `markAsNotRecovered`) con `NSwagLostItemRepository`, inyectado con `LostItemRepositoryProvider` y `useLostItemRepository()` (en `main.tsx`). `useClassLostItems(classId)` carga la primera página de la clase del hijo seleccionado y, con "Cargar más", las siguientes por cursor (sin duplicados); una **generación** (`generation`) se invalida al cambiar de clase o recargar, así que una respuesta o un error tardío de la clase anterior nunca llega a la nueva, y al cambiar de clase se reinician "cargando más" y su error. El estado **recuperado es del servidor y reversible**: `setRecovered(id, true|false)` llama a `markAsRecovered` o `markAsNotRecovered` con actualización optimista que se revierte (con mensaje en español) si falla. Los filtros de la página (alcance y estado) solo actúan sobre lo ya cargado, y si hay más páginas el mensaje de lista vacía lo dice. **Solo se crea con ámbito de clase** (el backend rechaza el ámbito colegio mientras no existan los roles de admin y de profesor, ver "Ámbito colegio cerrado en esta versión") y el botón "Nuevo" solo sale si el hijo tiene clase. **Quién marca como recuperado**: el backend lo permite solo al autor del objeto, así que `ItemCard` e `ItemDetailModal` reciben `canToggleRecovered` (`item.authorId === currentUserId`): el autor ve el botón y el resto solo ve una marca de «Recuperado» si ya lo está. **Ids**: el de un intento fallido se conserva ante un fallo de red, 5xx, 408 o 429 y se descarta tras éxito o un 4xx definitivo; un 409 recarga la lista y avisa con `UserFacingError` (ese aviso del 409 se comprobó a través de la API, aún no desde la interfaz). **Fotos (hueco conocido)**: la API solo guarda una URL (`photoUrl`, máx. 2048) y no hay endpoint para subir la imagen; la interfaz usaba URLs `blob:` locales que otros usuarios no pueden abrir, así que **se ocultó el campo de foto y nunca se envía `photoUrl`** (siempre `photoPrivacyConfirmed: false`); si la API devuelve un objeto con `photoUrl` se muestra. Habrá que decidir cómo subir imágenes antes de volver a ofrecerlo. Repetir el id de un objeto ya guardado (respuesta perdida y reintento) responde 409 en el backend, así que el aviso del 409 y la recarga de la lista se aplican.

El selector de **evento relacionado** de los avisos vuelve a estar activo con los próximos eventos puntuales de la clase (sin cumpleaños). **Verificado** en un Chrome real contra la API real, incluidas las zonas UTC+14 y UTC-8 sin desfase de día.
- **Deberes (`pages/Homework.tsx`, `modules/assignments`, `modules/subjects`)**: `IAssignmentRepository` (`listByClass`, `create`, `addComment`, `markAsDone`, `markAsNotDone`) con `NSwagAssignmentRepository` y `ISubjectRepository` (`listByClass`, `create`) con `NSwagSubjectRepository`, inyectados juntos con `HomeworkRepositoriesProvider` y `useHomeworkRepositories()` (en `main.tsx`). `useClassAssignments(classId)` carga la primera página (la API ordena por fecha de entrega ascendente y trae los comentarios dentro de cada tarea), pagina con «Cargar más» y descarta las respuestas y errores tardíos de otra clase (generación) también al cambiar de hijo; `useClassSubjects(classId)` carga las asignaturas. Un hijo sin clase muestra un mensaje y no hace peticiones. **Asignaturas**: la API solo tiene `{id, classId, label}` y **no hay catálogo por defecto**; solo el delegado de la clase las crea (en el formulario, «Añadir asignatura»), y un participante de una clase sin asignaturas ve que el delegado tiene que crearlas antes y no puede proponer. El color de una asignatura no existe en la API: sale de un hash estable de su id (`lib/subjectColor.ts`), no de su posición en la lista. **Oficial o propuesta**: lo decide el servidor (`isProposal`, `false` si quien crea es delegado de esa clase); la UI solo muestra la insignia «Propuesta». **No hay endpoint para aprobar** una propuesta, así que la UI no ofrece aprobarla. **Comentarios**: `addComment` crea el comentario con el usuario actual; se añade de forma optimista y se revierte con un mensaje en español si falla. **«Hecho»**: es una marca **personal y del servidor** (`PUT`/`DELETE /assignments/{id}/done`, idempotentes): cada usuario solo ve y cambia la suya, y se ve en cualquier dispositivo. Ya no existe `useDoneAssignments` ni el `localStorage`; las marcas que había guardadas en el navegador no se migraron. Los filtros de asignatura y de pendientes/hechas solo actúan sobre lo ya cargado y el mensaje de lista vacía lo dice cuando hay más páginas. **Verificado** en un Chrome real contra la API real (asignaturas, tarea oficial y propuesta, fechas sin desfase en tres husos horarios, comentarios con reversión, paginación con 29 tareas, otra clase, hijo sin clase, fallo de red al crear, respuestas tardías al cambiar de hijo y modo oscuro).
- **Gastos (`pages/Expenses.tsx`, `modules/classExpenses`)**: `IClassExpenseRepository` (`listByClass`, `create`, `markAsPaid`, `markAsUnpaid`) con `NSwagClassExpenseRepository`, inyectado con `ClassExpenseRepositoryProvider` y `useClassExpenseRepository()` (en `main.tsx`). `useClassExpenses(classId)` carga la primera página de la clase del hijo seleccionado (más recientes primero; cada gasto trae sus participantes con `hasPaid`), pagina con «Cargar más» y descarta las respuestas y errores tardíos de otra clase (generación). Los participantes se eligen de la lista de miembros de la clase (`useClassMembers`, que solo se pide mientras el formulario está abierto; un no miembro recibe un 403 que se muestra dentro del selector con «Reintentar»), por defecto todos. **Dinero**: el importe se escribe por familia y `lib/money.ts` lo convierte a **céntimos enteros** (`parseEuroAmount`), así que más de 2 decimales se rechaza en el formulario con un mensaje y el total nunca pasa por aritmética de coma flotante (`totalAmount = céntimos / 100`, máximo 99.999.999,99 €, la columna es `decimal(10,2)` y redondearía en silencio); se muestra con `Intl.NumberFormat('es-ES', EUR)` (`formatEuros`). El concepto admite 200 caracteres (límite del backend). **Evento relacionado**: `useUpcomingEventOptions(classId)` ofrece los próximos eventos puntuales de la clase (sin cumpleaños) y se envía `relatedEventId`. **Ids de creación**: ligados a la clase y al contenido exacto del formulario, se conservan ante fallo de red, 5xx, 408 y 429 y se descartan tras éxito o un 4xx definitivo; un 409 recarga y avisa con `UserFacingError`. - **Rol en la clase (`pages/MyClassRole.tsx`, `hooks/useClassRepresentatives.ts`)**: la página lista los delegados y las familias de la clase del hijo seleccionado con `useClassMembers`; el delegado ve «Hacer delegado/a», «Ceder el rol» y «Renunciar como delegado/a» (`assignClassRepresentative` / `resignClassRepresentative` de `IUserRepository`). **No hay traspaso atómico** en la API: «Ceder el rol» es nombrar a la otra persona y después renunciar (dos llamadas); si la renuncia falla, la otra persona ya es delegada, la UI lo dice y «Reintentar la renuncia» envía solo el `DELETE`. Máximo 3 delegados (`MAX_CLASS_REPRESENTATIVES` en `lib/roles.ts`, reflejado en el cliente: con 3 se desactivan nombrar y ceder) y el único delegado no puede renunciar (la API responde 400). Ceder y renunciar piden confirmación inline (`RepresentativeConfirm`). Tras cada acción se recargan los miembros y se llama a `refresh()` del contexto. Al renunciar, la BBDD conserva una fila de `UserClassRoles` con rol `Participant`. Un hijo sin clase muestra un mensaje y no hace peticiones. **Verificado** en un Chrome real contra la API real (64 comprobaciones: nombrar, ceder en dos llamadas, límite de 3, único delegado, renuncia, fallo parcial con reintento, sin red, 403 de un ajeno, cambio de hijo con petición en vuelo, privacidad del payload y modo oscuro). **Limitaciones conocidas**: tras un fallo de red o un 5xx en el paso de renunciar, la renuncia puede haberse hecho en el servidor aunque el mensaje diga que sigues siendo delegado/a, y cerrar ese aviso también elimina el botón de reintento; «Ceder el rol» no está disponible con 3 delegados porque el paso de nombrar lo rechaza el backend (haría falta un traspaso atómico). Ver «Review follow-ups added with T4.6» en `odd/tasks/frontend-api-integration.md`.
- **Patrón repositorio**, en `src/modules/<module>/`:
  - `domain/` — un fichero por tipo (nombre del fichero = nombre del tipo): el contrato del repositorio (ej. `IAnnouncementRepository`, en `domain/IAnnouncementRepository.ts`) contiene **solo la interfaz**, y cada tipo de dominio del módulo va en su propio fichero (`Announcement.ts`, `AnnouncementPage.ts`, `NewAnnouncement.ts`...). Los tipos compartidos entre módulos (p. ej. `PageRequest`) viven en `modules/Shared/domain/`. Sin ficheros índice ni reexportaciones: cada uno se importa desde su fichero. No depende de `infrastructure` ni del cliente NSwag.
  - `infrastructure/` — implementación concreta del repositorio (ej. `NSwagAnnouncementRepository`) que usa el cliente compartido de `modules/Shared/Infrastructure` para hacer las llamadas reales.
  - No se usa TanStack Query ni ninguna librería de caché de peticiones para esto.
- **Inyección de la implementación**: mediante un Contexto de React (mismo patrón que `ChildContext`/`ChildProvider`), no como singleton importado directamente ni instanciado a mano en el componente. Esto permite sustituir la implementación por un mock en los tests de `apps/test/frontend`. Componentes y hooks (en `components/app/`) consumen el repositorio a través de un hook propio (p. ej. `useAnnouncementRepository()`), nunca instanciando `NSwagAnnouncementRepository` directamente.
- Los mocks actuales de `src/data/*.ts` se sustituyen por `modules/<module>/` **módulo a módulo**, no todos a la vez.

## Patrones de UI ya establecidos (síguelos, no los reinventes)

- **Errores de render (`ErrorBoundary`)**: React solo captura errores de render en un componente de clase, y `Routes` (no es un router de datos) no tiene `errorElement`, así que hay dos capas, ambas en `components/layout/`: una **raíz** (`<ErrorBoundary fullScreen>` en `main.tsx`, por fuera de todos los proveedores) que muestra el aviso a pantalla completa, y una **por ruta** (`RoutedOutlet`, que sustituye al `Outlet` en `Layout` y `AppLayout`) que deja viva la barra y la navegación y se **reinicia al cambiar de ruta** (`resetKey={pathname}`). `ErrorFallback` ofrece «Reintentar» (vuelve a pintar) e «Ir al inicio» (un `<a href="/">` normal, no `Link`, para funcionar aunque falle el router) y aplica el tema guardado por su cuenta (con `try/catch`, para que el propio aviso no pueda fallar), porque a nivel raíz puede no haber montado aún ningún componente que use `useTheme`. **No captura** los errores de manejadores de eventos ni de promesas: esos los muestran los hooks junto a la acción que falló. No muestra la pila ni el mensaje del error al usuario (solo `console.error`). **Verificado** en un Chrome real forzando un error de render en una página y en la raíz (claro y oscuro, reintento, navegación que lo limpia). No hay test automático: no existe infraestructura de tests de frontend.
- **Modales**: `fixed inset-0 z-50 flex items-end sm:items-center justify-center bg-slate-900/40 backdrop-blur-sm` + tarjeta `rounded-t-3xl sm:rounded-3xl border border-slate-200 dark:border-slate-700 bg-white dark:bg-slate-900 shadow-xl`. Usa el truco del ref `mouseDownOnBackdrop` (solo cierra si el `mousedown` **y** el `click` caen sobre el propio fondo) para que seleccionar texto y arrastrar fuera del modal no lo cierre.
- **Desplegables/selectores personalizados**: nunca uses `<select>` nativo ni `<input type="date"/"time">` nativos — su popup no se puede estilar (bordes cuadrados, no respeta el modo oscuro). Usa/reutiliza `SelectDropdown`, `DatePicker` y `TimePicker` (`src/components/app/`), que renderizan su panel vía `createPortal` a `document.body` para no quedar recortados por el `overflow-y-auto` de un modal contenedor.
- **Filtros de página** (no dentro de modal): trigger tipo pastilla (`rounded-full`) + panel `absolute` con `onBlur` que cierra si el foco sale del contenedor (no necesitan portal al no estar dentro de un modal con scroll).
- **Marcas de estado (leído, hecho, recuperado, pagado)**: son del servidor y se cambian con actualización optimista sobre la lista ya cargada, que se revierte con un mensaje si la petición falla (`setRecovered`, `setDone`, `markAsRead`...); no las guardes en `localStorage` ni dupliques el dato en un estado paralelo.
- **Permisos por rol**: `useChildContext()` expone `currentRole`, `children`, `currentChild`, `otherGuardians`, `setCurrentChildId`. Compara `currentRole === 'classRepresentative'` para contenido oficial vs `'participant'` para propuestas/comentarios.
- **Modo oscuro**: `useTheme` alterna la clase `dark` en `document.documentElement` (`darkMode: 'class'` en `tailwind.config.js`). Todo componente nuevo necesita sus variantes `dark:` a la par que las claras, nunca solo un tema.
- **Privacidad de menores**: nunca mostrar apellido completo (solo inicial), nunca pedir/guardar año de nacimiento (cumpleaños solo día+mes), fotos de objetos perdidos con checkbox de confirmación explícita antes de publicar.

## Nomenclatura

- Inglés en todo el código: nombres de componentes, archivos, props, hooks propios y variables (`AnnouncementForm`, `eventsForDay`, `className`, `useChildContext`). Ver `docs/glosario-dominio.md` para traducir términos de negocio de forma consistente.
- Un componente por archivo, nombre de archivo = nombre del componente en PascalCase.
- Las interfaces (contratos/puertos, p. ej. los repositorios en `domain/`) llevan prefijo `I` (`IUserRepository`) y el fichero se llama igual (`domain/IUserRepository.ts`); su implementación contra la API se llama `NSwag<Entidad>Repository` (`NSwagUserRepository`, en `infrastructure/NSwagUserRepository.ts`) porque usa el cliente generado por NSwag; si algún día otra implementación usara otra fuente, llevaría su propio prefijo. Los tipos de datos (`Child`, `Profile`) no llevan prefijo y van **un fichero por tipo en `domain/`** (nombre del fichero = nombre del tipo, p. ej. `domain/Profile.ts`): el contrato `I<Entidad>Repository.ts` contiene solo la interfaz, y los tipos compartidos entre módulos (p. ej. `PageRequest`) viven en `modules/Shared/domain/`.
- Tipos/props inline en la firma del componente (`{ prop1, prop2 }: { prop1: X; prop2: Y }`), no interfaces `Props` separadas salvo que el tipo se reutilice en más de un sitio.
